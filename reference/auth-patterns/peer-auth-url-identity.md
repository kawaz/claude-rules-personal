# TLS を信頼の根にした peer 間相互認証

複数ホストに散った instance が mesh を組む時、**管理対象 (鍵素材・証明書・ノードごとの差分設定) を増やさずに**相互認証を確立する設計。信頼の根は Web PKI で、identity は「設定に書かれた endpoint URL」に置く。

## 前提

| # | 条件 | 満たさない場合 |
|---|---|---|
| P1 | 接続がステートフル (長命な全二重セッション) | この方式は成立しない。メッセージ単位署名 + リプレイウィンドウ + 鍵キャッシュという別方式になる |
| P2 | 各ノードが公開 FQDN と有効な TLS 証明書を持つ | 信頼の根が存在しない |
| P3 | 各ノードが全 peer の endpoint URL を設定として持つ | 照合対象が無い |
| P4 | 各 instance が起動時に自分の endpoint URL (`self`) を確定している | `aud` を検証できない (確定手段は別文書 `self-endpoint-identification`) |

P1 が本質。**接続確立時に一度だけ信頼を確立し、以降その接続の同一性は TLS が保証する**という性質に全面的に依存するので、鍵を使い捨てにでき、リプレイ記録も期限管理も残らない。

## 手順

C1 を張ってハンドシェイクを開始した側を S、受けた側を R とする。役割はこの一点で決まる。C2 は R が dial する短命の接続で、鍵取得と challenge 交換だけに使い 1 往復で閉じる。

```
 1. C1   S ──▶ R   wss 接続確立 (S は TLS サーバ証明書で R を認証)
 2.      S         エフェメラル鍵ペアを生成し kid を採番、取得可能にする
 3. C1   S ──▶ R   hello { ver, iss, aud, kid, id }
 4.      R         iss / aud を設定と照合。NG なら close
 5. C2   R ──▶ S   接続確立 (R は TLS サーバ証明書で S を認証)
 6. C2   R ──▶ S   jwk_req { kid, challenge }
 7. C2   S ──▶ R   jwk_res { jwk }
 8. C2             close
 9. C1   S ──▶ R   proof (JWS: challenge を署名)
10.      R         署名検証。NG なら close
11.      R         C1 を「S からのもの」として確定
12. C1   R ──▶ S   ack
13.      S         鍵を破棄。以降メッセージ送信可
```

hello は署名されないので、そこに書かれた値は何も保証しない。役割を持つのは proof のクレームで、`iss` が識別、`aud` がリレー攻撃 (正規 peer R′ が S から受けた署名を本物の R に転送する) の防止、`challenge` がリプレイの防止、`exp` がハンドシェイク段階の寿命の上限を担う。

S は **ack を受けるまでメッセージを送ってはならない**。R が ack より前のメッセージを受けたらその接続を close する。ack が無いと R は検証完了前のメッセージをプールする必要が生じ、バッファ管理・上限・タイムアウトを抱え込む。

## 信頼の連鎖

初期状態で双方が信頼しているのは、設定の endpoint リストと CA の 2 つだけ。

S 側: 設定への信頼で `aud` が接続してよい URL だと信頼する → `aud` の TLS で C1 を信頼する → **C1 の相手が `aud` であることを信頼する**。TLS のサーバ証明書検証だけで S 側の認証は閉じている。以降の手順が R 側の認証しか扱わないのはこのためで、基盤を差し替える時はこの保証がどこから来ていたかを確認する。

R 側: hello の時点では何も信頼しない → 設定への信頼で `iss` が接続してよい URL だと信頼し、同時に `aud` が `self` と一致することを確認する → `iss` の TLS で C2 を信頼する → C2 への信頼で `jwk` を信頼する → `jwk` と proof の検証で C1 を信頼する → **C1 の相手が `iss` であることを信頼する** → C1 への信頼で **遡及して hello の内容を信頼する** (`kid` が S の採番したものだと確定し、取得した `jwk` が S の用意したものだったことが裏づけられる)。

最後の遡及の規則が、hello に載せた他の名乗り (後述の instance id) も proof の後で信頼できる根拠になる。

## `iss` / `aud` は URL の完全一致

TLS が認証するのは FQDN までで、同一 origin 内の別 instance を区別しない。`wss://h.example/a` と `wss://h.example/b` は TLS から見れば同一主体である。`iss` / `aud` を **パスを含む URL の完全一致**で相互検証することでこの粒度差を埋め、1 つの origin に複数 instance を相乗りさせられる。

- 前方一致・部分一致にしない。`wss://r.example.evil` を弾くため、かつ origin 単位の比較は相乗り時に別 instance を取り違えるため
- 相乗りする instance 同士が互いに**信頼境界**を成すかは別問題。同一プロセス内の論理 instance なら `iss` / `aud` は識別子として機能するだけで境界にはならない。境界にするにはプロセス分離・鍵素材の分離・鍵配布の分離が要る

### 鍵取得は C2 で、鍵空間は `iss` ごとに分離する

鍵は **認証対象の接続 (C1) の外側で取る**。C1 上で要求すると循環し、攻撃者が自分の鍵を返して自分の署名を通せる。信頼の根は認証対象の接続の外側になければならない。

取得先は **instance ごとに分離が必須**。`wss://h.example/a` と `/b` が origin 単位の共通鍵空間を共有すると、b が自分のエフェメラル鍵をその空間に登録し、`iss: .../a` を名乗って R に接続し、R は a の鍵取得先を引いて b の鍵で検証に成功してしまう。`iss` の検証は、その `iss` に対応する鍵空間が分離されて初めて意味を持つ。取得先を `iss` のパス配下に置く、`iss` のハンドラ自身に応答させる、といった構成は構造的にこれを満たす。

鍵は接続ごとに生成して使い捨てる (ローテーションの概念を持たない)。破棄契機は ack 受信かセッション終了の早い方で、生存数は同時ハンドシェイク数に等しく自然に上限が付く。鍵取得は認証前の生の接続なので rate limit を入れる。集合 (JWK Set) ではなく `kid` 単位で配る — 集合を返すと同時接続数が外部から観測できる。

### glare / ハートビート / 再接続

- 双方が対等に dial するので 2 本張られうる (glare)。**両方を検証したうえで**、`iss` 文字列の小さい側が dial した接続を残す。比べるのは endpoint URL で、優劣ではなく「両端が同じ 2 本の文字列を比べて同じ結論に至る」ことだけが要件。畳む前に両方検証しておくと、残る 1 本が認証済みであることが保証される。close code は glare 由来と分かるものにし、相手はそれを再接続契機にしない
- ハートビートは必須 (中間 box による無通知切断の検出)
- 再接続のバックオフは緩くてよい。相手が復旧すれば相手から dial してくる。dial 責務を片側に割り当てると、その側が落ちている間に生きている側から復帰させる手段が無くなる
- peer の除名は確立済み接続に反映されない。認証が接続時 1 回である以上、除名時に該当接続を明示的に close する経路が要る

## id と endpoint の分離

endpoint URL を identity そのものにすると、instance の引っ越し (URL が変わる) で、その URL を鍵にした永続データが全部無効になる。identity は **state と一緒に引っ越す固定の乱数 id** に置き、URL は「今どこで待っているか」に留める。

- **instance id**: 初回起動時に生成して state に保存する乱数。state ごと持って引っ越す
- **endpoint**: 設定の `self` (自分) と `peers` (相手) に書く URL。TLS と `iss` / `aud` の照合値はこの URL のまま (信頼の根は URL にしか無い)

handshake で相手は自分の id を名乗り (hello に足す。proof の後に hello が遡及して信頼される規則に乗る)、受けた側は **「認証済み endpoint ↔ id」の対応表**を持つ。dial した側は相手の hello 応答から同じ束縛を作る — この向きで名乗りを裏付けるのは、dial した URL の TLS である。

**1 つの id が束縛できる endpoint は 1 本だけ。** 束縛表は自分の `(self, 自分の id)` で初期化する (= 自分の id を名乗る peer も拒む)。既に別の endpoint に束縛済みの id を名乗る hello は、**新しく来た側を close する**。名乗りを裏付けるものは operator が配った endpoint リストしか無いので、そのリストが既に裏付けた束縛の方を残す。引っ越した instance の旧 URL がまだ生きている場合がこれに当たり、直し方は各 peer の `peers` から旧 endpoint を外すことであって、新しい link を勝たせることではない。**全 peer のリストを更新して回るのが引っ越しの必要コスト**で、これを避けようとすると「名乗ったもの勝ち」になる。

id で鍵付けするものと URL で照合するものは、はっきり分ける:

| id (固定) で鍵付けするもの | URL (可変) で照合するもの |
|---|---|
| メッセージ id の instance 部分 | TLS のサーバ証明書検証 |
| 複製する record の発行者 (`iss`) | hello / proof の `iss` / `aud` |
| kv / inbox / 死活記録の鍵 | 鍵取得先の導出 |
| op 転送の宛先 (`to_instance`) | glare の勝敗比較 |

id を持たない行も一覧に出す。config が挙げた peer は handshake 前でも一覧に出すべきで (まだ誰も名乗っていないので id は空)、id を持たない行を隠すと link が落ちている peer — 読み手がまさに探している行 — が消える。

## endpoint リストが唯一の信頼源

- `self` と一致しない URL で来た mesh の hello は `aud` 不一致で拒否する。別名 FQDN や LB を経由して届いた mesh 接続は、それだけで落ちる
- **人の入口は `self` を名乗らない**ので、どの FQDN 経由で来ても token だけで判定できる。人の入口 (`/ws`、`/auth/*`、webhook) のルートは **パスの末尾で照合し prefix を問わない**。proxy は prefix を剥がさずそのまま渡し、cookie の Path は request のパスから取る。これで別名 endpoint や LB が `self` と無関係に成立する
- **mesh のルート (probe、鍵取得) だけは `self` のパス配下に固定する**。鍵空間の分離がそれを要求するため。人の入口まで `self` 配下に縛ると、別名 endpoint と LB で 404 や cookie Path 不一致になる
- 未認証の相手に endpoint URL を見せない (challenge に埋めるのは id の方)

## 制約と適用範囲外

- **契約の世代**: `instance` フィールドの意味が「endpoint URL 完全一致」から「opaque な id」に変わるのは互換を切る変更なので、プロトコルの世代を上げる。id と endpoint を別の型として定義し、id の文字集合に合わせた pattern を持たせる。mesh を持たない instance は名乗る URL が無いので、endpoint フィールドは optional
- **権限分離**: このプロトコルが答えるのは「誰か」だけで、「何をしてよいか」は上位レイヤ。転送された要求も転送先で認可を通し直す (「A が認可したから B は信じる」にしない。A が侵害された場合に B の認可が消えるため)
- **ホストを掌握された正規 peer**: 信頼の根が Web PKI である以上、FQDN を制御する者は正当な peer である
- **TLS 終端より内側の区間**: 保証されるのは「この接続は S の TLS 終端点を通って来た」まで。終端がアプリ自身か前段の LB かは関知せず、内側の完全性はネットワークの運用者の責務

## 不採用

| 方式 | 理由 |
|---|---|
| mTLS | 証明書の配布・更新という管理対象が増える。加えて public CA の clientAuth EKU は廃止済みで private CA の運用が必須になる |
| Noise IK / WireGuard / 公開鍵の設定直書き | 相手の静的公開鍵を全ノードに事前配布することになり、管理対象を増やさない目的と真逆 |
| Noise XX | 事前共有は不要だが、交換した鍵を FQDN に紐づける仕組みが別途要る。それが結局 PKI なら TLS の上に重ねる二度手間 |
| SPKI pinning | ピン値の配布と更新という管理対象が生まれる |
| challenge を独立した往復で送る | C2 が元々必要なのでそこに相乗りさせれば往復が増えない |
| TLS exporter で challenge を不要にする | TLS 終端がアプリ自身である構成を要求し、LB 終端を許さなくなる |
| `jti` + 受信側のリプレイ記録 | 記録の保持と期限管理という状態が増える。ステートフル接続なら challenge を接続に従属させると状態が消える |
| id を endpoint URL (やそのハッシュ) にする | 引っ越しで record・メッセージ id・kv の鍵が全部無効になる |
| 検証を迂回するテスト用フラグ | 迂回路が本番バイナリに残る。テスト用 CA を信頼ルートに注入すれば同じことが迂回路なしでできる |
