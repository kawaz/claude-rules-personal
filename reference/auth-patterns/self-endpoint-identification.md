# 自分の endpoint を確定する

peer 間認証で `aud` を検証する側は、自分の endpoint URL (`self`) を知っている必要がある。`aud` の照合対象であり、自分が名乗る時の `iss` でもあるので、送信側と受信側で同じ値を使う。ここでは `self` の確定手段を扱う。

## 原則: 接続やリクエストから自分を逆引きしてはならない

`Host` ヘッダは接続元が指定する値であり、前段に LB や proxy を挟めばパスも書き換わる。どちらも自己識別の根拠にならない。リスニングソケットからも「どの URL 経由で到達されたか」は分からない。

相乗り構成 (1 origin に複数 instance) では instance ごとに `self` が異なる。1 プロセスが複数 instance を提供する場合、どの instance として応答しているかは socket からは判別できないので、**ハンドラの生成時に `self` を束縛**しておく。

## 方式 (a): probe による自己識別

起動時に、候補集合 (`peers`) のうちどれが自分かを照合で決める。

```
1. 各 peer_i に対し token_i = random(128bit) を生成し、対応表に記録
2. peer_i へ probe { ver, token: token_i } を送信 (全て並行でよい)
3. 自分のハンドラに届いた probe の token を対応表と照合
4. 一致した i の URL を self とする
5. 全リクエストの完了後、対応表を破棄
```

送信も受信も同一プロセスで行う。自分宛の 1 通は自分に届き、他は他ノードに届く (他ノードの対応表にはその token が無いので照合は外れる)。probe の受理に認証は要らず、受けた側は自分宛かどうかに関わらず応答してよい — 照合するのは送信側だから。

**probe は TLS 上で送り、サーバ証明書を検証しなければならない。** token は推測できないが傍受はされうる。経路上で盗んだ `token_i` を送信元自身へ送り返されると、送信元は自分を `peer_i` だと誤認する。TLS があれば `token_i` は `peer_i` にしか到達しない。token は TLS 内では平文でよく、追加の署名も要らない (傍受された probe の送り返しは署名でも防げないので、鍵の生成・配布・検証というコードパスが増えるだけになる)。

**自分宛の probe を送信対象から省略してはならない。** 悪意ある正規 peer が受け取った `token_i` を送り返す攻撃は TLS では防げない (証明書は正当なので)。これが不成立に終わるのは、送信元が自分自身にも probe を送っており、その 1 通は必ず自分に届くからで、攻撃者は自分宛 probe に介入できず一致数が必ず 2 以上になる。誤認ではなく起動失敗 (可用性の低下) に落ちる。

判定は一致数で行う:

| 一致数 | 判定 |
|---|---|
| 1 | `self` が確定 |
| 0 | 起動失敗 (自分が候補に含まれていない / URL の typo / 外から自分へ到達できない) |
| 2 以上 | 起動失敗 (同一ホストが別名で複数登録、DNS が複数の名前を同じ宛先へ) |

2 以上を先着優先などで自動選択してはならない。どちらが正式な名前かはプロトコルから決められず、握りつぶすと `aud` 検証が後から不定に失敗する原因になる。

**到達しない peer を一致数の計算から外す緩和**は入れてよい。ノードが常時起動しているとは限らない運用 (片方の PC が寝ている、が常態) では、到達しない peer で起動を止める意味がない。誤認を防ぐ性質は「自分宛は必ず届く」にしか依存していないので、この緩和で崩れない。答えなかった peer は記録するだけにして、dial 対象には残す。

## 方式 (b): config への直書き

`self` を設定ファイルに直接書く。ノードごとに設定が異なる (差分管理という管理対象が増える) のが代償で、方式 (a) はそれを避けるために存在する。

**直書きへ切り替える条件**は、proxy / 別名 / LB の裏に居て、**自分の公開 URL が socket からも probe からも一意に決まらない**構成になった時。具体的には、入口を利用者が用意した任意の URL にできる、1 つの origin の裏に複数 instance を相乗りさせる、同じパスで複数 instance を LB で束ねる、といった構成では、probe の一致が 2 以上になったり、そもそも外形の URL が候補集合に無かったりする。この時点で「探索で決める」は成立しない。

## 直書きにした後も probe を残す

`self` を config に持っても、probe は捨てずに**起動時の検証**として残す価値がある。決めるのは identity ではなく、設定の正しさと peer の到達性:

- **`self` に送った probe が自分に返ること** = `self` が他人を指しておらず、誰も居ない URL でもないこと。返らなければ壊れた config として起動を止める
- **各 peer の到達性の記録** = 一覧の typo と疎通を起動時点で露見させる。答えなかった peer は記録するだけで起動は止めない

この形なら `peers` に自分の URL や別名が入っていてよい (同じ設定ファイルを全ホストに配れる)。自分に返ってきた分は dial しないだけで済む。

`self` を持つのは mesh を組む instance だけで、**mesh を持たない instance は名乗る URL が無い** — 一覧に出る行は endpoint を持たず、`hello` でも endpoint を返さない。設定項目としても optional にする。

## 起動順序との関係

probe の中身は「`self` に送った probe が自分の listener に届くこと」なので、**listen より前には置けない**。順序は「WS を先に bind する → probe で検証する → 残りの初期化 → 安定 path の公開」になる。

検証中の listener が答えてよいのは probe と鍵取得の 2 経路だけで、それ以外の要求は「まだ準備できていない」として断る。窓は probe 1 往復分しかないので、この間に人の要求を受ける必要はない。

`self` が他人を指していれば起動失敗、答えなかった peer は記録して dial 対象に残す。設定ミスは起動時に落とし、実行時に持ち越さない (機能を黙って無効にして起動を続けると、「設定したはずの機能が効いていない」状態が実行時まで隠れる)。

probe を既存のリスナーに相乗りさせる時は、認証済みメッセージと区別できるようにする。peer 間認証は「ack より前のメッセージを受けた接続を close する」ので、probe を同じ経路に流すと**自分の probe で自分のハンドシェイク接続が切られる**。専用のパスにするか、接続確立直後に判別できるメッセージ型として分離する。

## 適用範囲外

- **peers の継続的な到達性監視**。起動時点のスナップショットしか取らない。死活監視は認証プロトコル側のハートビートが担う
- **自分の URL が外部からどう見えるかの一般的な解決**。NAT や複数 IP を持つ環境で確定できるのは「候補集合のうち自分に到達したもの」であり、それ以上ではない
- **probe 送信元の認証**。probe は認証前に処理され、受理しても状態を持たないので認証を要求しない
- **TLS を張らない経路**。誤認を誘導されるので対象外
