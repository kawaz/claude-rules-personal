# 複数タブで access token を共有しながら refresh する

access token が「ページのもの」ではなく「利用者の token family のもの」である設計 (`passkey-registration-local-first` の「token は署名しない opaque 値」) では、同じ人が開いた複数のタブが同じ 1 本の access を提示する。ここではその 1 本を壊さずに refresh する手順を扱う。

## 問題: refresh のたびに access を差し替えると往復が始まる

タブ A が refresh して family の access が新しい値になると、タブ B が持っている値は無効になる。B は次の提示で拒否され、refresh し、今度は A の値が無効になる。以後、開いているタブの数だけこの往復が続き、family の rotate も同じ回数だけ回る。

「ローカルの期限を信じない」「拒否されたら refresh する」だけではこれは止まらない。**止めるには、refresh を 1 本に絞る (クライアント側) か、差し替え自体を減らす (サーバ側) かのどちらかが要る。両方入れる**: クライアント側は協調が効かない環境があり、サーバ側だけでは rotate の回数を減らせない。

## 手順 (クライアント)

### 1. refresh は排他ロックの中でだけ行う

同一 origin のタブ間で共有される排他ロック (Web Locks API の `navigator.locks.request()`) の中で refresh する。1 セッションにつき同時に 1 タブだけが走る。

ロック名には **endpoint (認証の単位) と利用者 (sub) を含める**: `<名前空間>.auth.refresh:<endpoint>:<sub>`。1 つの origin が複数の endpoint を、1 つの endpoint が複数の人を持ちうるので、id を含まない固定名にすると無関係なタブ同士が待ち合う。

### 2. 得た access は配布するが永続化しない

同じキーの BroadcastChannel (`<名前空間>.auth:<endpoint>:<sub>`) で他のタブへ配る。**メモリからメモリへ渡すだけ**で、storage には書かない — 書いた瞬間、その origin で走る任意のスクリプトから読める値になる。

### 3. ロックを取った側は refresh の前に「持っている?」と尋ねる

channel に問い合わせを投げ、期限内の access が返ってきたら refresh しない。**聞く側に回ることが要る理由は 2 つ**:

- ロックと message は別々の queue で渡る。前のタブが配ったものが、ロックを取った時点で届いているとは限らない
- 読み込み直後のタブは、自分が存在する前に配られたものを受け取れない。listen しているだけでは永久に届かない

答えが無ければ短い打ち切り (数十 ms。同一 origin の message 往復に主スレッドの混み具合を足した程度) の後、自分で refresh する。**打ち切りを待ち切るのは「このセッションで開いているタブが自分だけ」の時だけ**で、その時に遅らせているのはどうせネットワーク往復を使う refresh なので損がない。

### 4. 拒否された時の順序

提示した access を handshake が拒否した時は、次の順に落ちる。

1. 他のタブが配った直近の access (期限内なら) を提示し直す
2. ロック付き refresh
3. 再認証画面

**backoff ループに入らない**。拒否 → 待つ → 同じ値を再提示、は往復を遅くするだけで解消しない。

### 5. sub が分かる前は endpoint だけのキーを使う

まだ認証していないタブは自分の sub を知らない。endpoint だけのキーで待ち、sub が確定した時点でロック名と channel を張り替える。配るメッセージには sub を載せる — endpoint だけのキーで聞いているタブは、名前から sub を読めない。

### 6. Web Locks が無い環境

各タブが自分で refresh する。手順 4 だけが残り、収束はサーバ側の据え置きが担う。**協調はこの挙動を改善するものであって、成立の前提ではない**。

## 手順 (サーバ)

refresh で access を毎回差し替えない。**standing の access の残り寿命が TTL の半分以上あれば、それをそのまま返す**。半分を切って初めて mint し直す。

- 複数のタブが同じ access を持てるので、クライアントのロックが取りこぼした分の保険になる
- 半分という閾値は、「新しい値に気づくための猶予」として取れる最大値
- **refresh token 自体は毎回 rotate する**。据え置くのは access だけで、再利用検知は refresh の世代交代に依存している

## 手順が守る性質 (テストで固定する)

| 性質 |
|---|
| 2 つのタブの access が同時に切れても refresh は 1 回だけ走る |
| refresh したタブの結果が、待っていたタブにも届く |
| 期限切れの値は配らない (受けた側も提示に使わない) |
| 開いたばかりのタブは、問い合わせで既に立っている値を受け取る |
| 誰も答えなければ自分で refresh する |
| ロックが無い環境では各タブが自分で refresh する |
| endpoint が違うタブ、sub が違うタブとは調停しない |

## 不採用

| 案 | 理由 |
|---|---|
| localStorage で token を共有する | 永続化した時点で漏洩面が増える (メモリ間の配布ならタブが閉じれば消える)。storage event には順序保証も配送保証も無く、調停の土台にならない |
| サーバ側で複数の access を同時に有効にする | 失効させる単位が増える。「この family を今すぐ止める」が「立っている値を全部数え上げて消す」になる |
| refresh 役を 1 つのタブに固定する (leader 選出) | leader のタブが閉じた瞬間に壊れる。生存監視と再選出という、ロックが最初から持っているものを自作することになる |
