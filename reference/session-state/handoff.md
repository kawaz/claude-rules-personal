# セッションの引き継ぎ (ライブ)

作業を新しいセッションへ渡す時の既定の手順。旧セッションが生きているうちに同じ cwd で新セッションを起こし、引き継ぎの本文を ccmsg の `send` で直接渡す。新は不明点を旧に聞け、旧は答え切ってから止まる。

状態ファイル (reference の `session-state/write` / `session-state/load`) は、旧が生きていられない時 (`/clear`、compaction、クラッシュ前、ハーネス再起動) か、相手を今起こせない時 (ccmsg の launch が無い環境等) だけのフォールバック。

ccmsg の tool (`launch` / `peers` / `send` / `say`) の field の決まりは `ccmsg` skill にある。

## 旧セッションの手順

### 1. 永続化ファースト (本文を書く前に)

`send` の本文は新の会話にしか残らず、新が compaction されれば要約に潰れ、旧が落ちれば聞き直す先も無い。**本文は永続知識の置き場ではない**。書き始める前に、現コンテキストにしか無い以下をリポ側へ落とす (分類は reference の `docs-authoring/knowledge-timing`):

- 確立した手順・復旧手順 → `docs/runbooks/`
- 調査で確定した事実・数値 → `docs/findings/` / `docs/knowledge/`
- ハマり所と解決のペア → `docs/journal/`
- 未決の論点 → `docs/QUESTIONS.md` / `docs/issue/`

落とした後、本文からは**参照で指す** (本文を二重化しない)。この順序を守ると継続作業指示の多くが「`<doc>` を読んで実行」の 1 行になる。

### 2. 自分で閉じる範囲を決める

旧が自分で終わらせた方が速く安全な作業は、旧の担当として残してよい。典型は次の 2 つ:

- 走行中の worker / background task の結果の受け取り (ハンドルは旧にしか無い)
- commit 直前まで進んだ作業 (差分の意図を知っているのは旧だけ)

範囲は本文の「旧が自分で閉じるもの」節に、対象 (ファイル・worker 名・task id) と終わりの形 (commit する / issue を更新する等) で書く。新はその範囲に触らない。閉じる範囲以外の新しい作業は旧で始めない。

### 3. 新セッションを起こす

`launch` で起こす。

- `cwd`: 自分の cwd (同じ cwd)
- `model` / `effort`: 自分と同じ
- `name`: 役割 + 起動時刻 (例: `main-20261109-1430`)
- `prompt`: 「旧セッション `<自分の session_id>` から引き継ぎの本文が ccmsg で届く。cwd の起動手順 (CLAUDE.md 等) を踏んでから本文を読み、reference の `session-state/handoff` の受け側の手順で引き継ぐ」の趣旨だけを書く

本文そのものは `prompt` に入れない。`prompt` は新で人の入力として読まれるので、`[AI 自律]` の項目まで人の指示の重みで流れる。本文は `send` で渡し、受け側のラベル分岐を通す。

`exit_code` が 0 でも立ち上がったとは限らない。`peers` (`cwd_prefix` に自分の cwd + `/`) に新の `name` が載ったのを確かめ、その `session_id` を控える。

### 4. 本文を送る

`send` は新の `session_id` で宛てる (`cwd` で宛てると旧以外の同 cwd のセッションにも届く)。本文の節立ては下の「本文のテンプレ」。新から受領の返事が来るまで送り直さない (「確かめられなかった」で返った時に送り直すと二重に届く)。

### 5. worker を渡すか止める

- 渡す worker には、旧が SendMessage で「新しい統括のセッション id は `<新の session_id>`。以後の報告は `mcp__ccmsg-v1__send` (`session_id` に新の id) で送る」と伝える (worker の SendMessage は旧の統括にしか届かない)
- 渡さない worker は TaskStop で止める。走らせたまま旧が止まると、ccmsg 上で誰の worker か分からないものが残る

### 6. 答え切って止まる

- 新から質問が届いたら答える (返事は `send` で、宛先は封筒の `from` の id)
- 閉じる範囲を終えたら、新に完了を送る (commit hash、更新した issue のパス、worker の結果の置き場)。終わらせられなかったものは、その状態 (どこまで進んだか、残りは何か) を送って新に渡す
- 全部終えたら、自分の Monitor / background task / Cron を止め、ユーザに「**このセッションは閉じて良いです。**」とだけ知らせる (チャットでも `say` の音声でも同じ文)。プロセスの終了はユーザが行う
  - 「旧い統括のセッション」のような書き手から見た呼び方をしない。ユーザからは旧も新も同じ名前の並びに見え、どちらを閉じてよいか分からない。「この」セッションと言えば、言われた側の画面で一目で分かる
  - セッション名の日時などの数字を添えない (見比べるのが手間になる)。後継に触れる必要があれば「後継のセッション」で足りる

## 本文のテンプレ

状態ファイルの 10 セクション (reference の `session-state/write`) の短縮版。該当なしの節は「なし」と書く (漏れと区別するため)。文体はゼロコンテキストの初見読者向け (略語・セッション内の造語を持ち込まない)。

```
1. 現在地         — 大目標と現在地 (1〜2 文)、各リポの head (コミット hash)、未コミット変更の所在と誰が commit するか
2. ユーザ裁定     — このセッションで出た裁定・確定を原文の要点で (DR / issue / QUESTIONS.md への参照付き)
3. 禁則           — 安全制約・gate・運用ルール (特定モデルの使用禁止のような、知らないと事故るもの)
4. 旧が自分で閉じるもの — 対象と終わりの形。新は触らない
5. 継続作業指示   — 新が引き継いで即やる作業。無いなら「なし (次の候補: ...)」と断定する
6. peer と worker — 文脈が温まっていて引き続き役に立つ worker は「旧の session_id + worker の agent_id + 何を担当しているか」を渡す (新はそこへ ccmsg の `send` で話しかける)。
                    それ以外の worker は旧が TaskStop で止めてから渡す (ccmsg 上で生きている worker = 引き継いだ worker になる)。新しく起こす時のために「再 spawn 手順」(agent 定義名・使い分けの実績・委譲プロンプトの型) も書く。
                    連携中の別セッション (ccmsg peer) は「session_id + cwd + 交わした約束」
7. 失敗したこと   — 試して駄目だった事と理由
```

### 継続作業指示の書式

各項目の先頭に**出どころラベルを必ず付ける** (受け側はラベルで分岐する):

- `[ユーザ 指示]` — ユーザが明示的に指示・承認した作業。**根拠となる発言の要点を併記する** (例: 「kawaz『Release 出すところまでやって』2026-08-20」)
- `[AI 自律]` — このセッションの AI が自己判断で立てた作業。判断の根拠 (どの観測 / どの issue から導いたか) を併記する

判定に迷う項目は `[AI 自律]` にする。書く時点でその作業が**既存の DR / 裁定を覆すもの**だと気づいたら、継続作業指示に書かず `docs/QUESTIONS.md` の裁定待ちへ回す (AI が単独で裁定を撤回しない)。

**粒度**: 1 項目 = 1 検証可能単位 (完了をどう確認するかが 1 行で書ける粒度。reference の `delegation/orchestration-phases` Phase 0 と同じ基準)。手順は runbook / issue に落として「`docs/runbooks/<file>` を読んで実行」「`docs/issue/<file>` の次の一手」の参照形で書く。落とすほどでない手順は具体的な実行コマンド例と結果の見方まで書く。

## 担当の分割と同居中の扱い

旧と新が同じ cwd に居る間、作業の持ち主は次で決まる:

- 旧: 本文の「旧が自分で閉じるもの」と、新からの質問への返答だけ
- 新: それ以外の全部

同 cwd に 2 セッションが居る間に入ってくる外部入力 (定期の差し込み、`cwd` 宛ての `send`、hook の通知等) をどちらが受けるかは、**プロジェクト側の責務**で、この規約では扱わない (cwd 宛ての `send` は両方に届く)。プロジェクトに振り分けの決まりがあればそれに従う。

## 受け側 (新セッション) の手順

1. **起動手順を先に踏む**: cwd の CLAUDE.md 等の起動手順を済ませてから本文を読む (本文が先に届いていても順序は変えない)。本文を受けたら旧に受領を `send` で返す
2. **状態ファイルは探さない**: `send` で本文を受けたら、未消費の `latest.md` が残っていても採用しない (2 経路から立ち上がると状態が分岐する)
3. **鮮度を見る**: 本文の「現在地」の head を実機 (`jj log -r main` / `git log`) と照合する。旧の閉じる範囲の commit 以外で進んでいたら、継続作業指示は失効扱いにして実行せず、実機確認の結果と次アクション候補の提示に降格する (別セッションが消化した可能性が高い)
4. **継続作業指示をラベルで分岐する** (下の節)
5. **不明点は旧に聞く**: 推測で埋めず、旧に `send` で聞く (宛先は本文の封筒の `from` の id)。旧が生きているうちに聞かないと取り戻せない
6. **渡された worker には ccmsg で話す**: 本文に書かれた `session_id` (旧) + `agent_id` を `mcp__ccmsg-v1__send` に付けて送る。`agent_id` は spawn 結果の内部値で `peers` には載らないので、本文に書かれたものだけが手掛かり。worker からの返事は新の会話に `ccmsg:<旧の session_id> から:` の印付きで届く
7. **旧の閉じる範囲は待つ**: その範囲のファイル・worker・issue に触らない。旧から完了の連絡が来たら、hash 等を実機で確かめて引き継ぐ。終わらせられなかった分が送られてきたら、それを自分の作業として引き継ぐ
8. **旧が居なくなった時**: `peers` から旧が消えた、または質問に返事が無いまま旧が落ちた時は、reference の `session-state/load` の手順で状態ファイルを探す。無ければ journal / メモリ / リポの実機確認から立ち上がる。旧の閉じる範囲が完了連絡なしに残ったら、実機 (`jj status`、issue、worker の出力) で現状を確かめ、引き継ぐかをユーザに確認する

### 継続作業指示の扱い (ラベル分岐)

状態ファイルで受けた時も同じ分岐をする。継続作業指示が**無ければ**次アクション候補の優先度を提示してユーザ判断待ち。**あれば**項目ごとの出どころラベルで分岐する (Monitor 等の再起動指示があればここで済ませる):

- `[ユーザ 指示]` — 暗黙 approve として即実行 (ユーザの追加確認を待たない)
- `[AI 自律]` — 着手前に**根拠の裏取り**をする。当該作業が触る領域の DR / issue / `docs/QUESTIONS.md` の裁定サマリを grep し、**確定裁定と矛盾しないこと**を確認してから実行する。矛盾を見つけたら実行せず、矛盾点を添えてユーザに確認
- **ラベルが無い** — `[AI 自律]` と同じ扱い (安全側に倒す)

> Why: 継続作業指示は「最新のユーザ意図」として即実行される経路。前セッションの AI が自己判断で立てたタスクが同じ重みで流れると、確定済み裁定を AI が単独で覆した結果が、ゼロコンテキストの後継で裏取りされずに実行される。ラベルは「誰の意図か」を後継が復元できる唯一の手掛かりになる。

## 費用と弱点

- **同居中は 2 セッション分の費用がかかる**: 旧は質問に答えるために context を抱えたまま生きる。閉じる範囲は小さく保ち、答え終えたら待たずに止まる
- **旧が落ちてからの渡し漏れは取り戻せない**: 本文に書かなかったことを、落ちた旧に聞き直す手段は無い。担保は永続化ファースト (1.) で、本文はリポ側の文書を指す参照にしておく
- **本文は新の会話にしか残らない**: 新が compaction されると要約に潰れる。新は受けた本文のうち後で要るもの (裁定・禁則) を、自分の作業の中でリポ側へ落とす
