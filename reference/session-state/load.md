# セッション状態ファイルのロード

前のセッションが残した状態ファイルを、後継セッションが 1 回だけ引き継ぐための手順。

ファイルを探すのは、引き継ぎの本文が ccmsg の `send` で届いていない時だけ。`send` で届いたならファイルは探さず reference の `session-state/handoff` の受け側の手順に従う。ファイルを探すのは次の時:

- `/clear` や compaction の後 (同じセッションが自分の書いたファイルを読み直す)
- ライブ引き継ぎの旧セッションが落ちた (`peers` から消えた、返事が無い)
- 起動の指示が状態ファイルのロードを求めている (launch の無い環境での起動、ハーネス再起動後)

## 場所とポインタ

```
${XDG_CACHE_HOME:-$HOME/.cache}/claude-session-state/<project>/latest.md
```

`<project>` は**リポジトリのディレクトリ名そのまま** (前方一致する姉妹リポは別ディレクトリ)。`latest.md` は本文を持たないポインタ:

```
repo: /abs/path/to/repos/github.com/<owner>/<repo>
state: <YYYYMMDD-HHMM>.md
loaded_by:
```

- `repo:` — この状態ファイルが管轄するリポの絶対パス (照合キー)
- `state:` — 状態本文の実体ファイル名 (同ディレクトリ、immutable)
- `loaded_by:` — 引き継いだセッションの記録。空なら未消費

## 手順

1. **cwd 照合**: 自分の cwd が `repo:` 配下でなければ、別プロジェクトの状態ファイル。読まなかったことにして通常立ち上げする (姉妹リポの state を誤って引き継ぐのが最悪の事故)。`repo:` が無い形式は状態本文の §2 Current Phase のリポ名で同じ照合をする
2. **鮮度チェック**: 状態本文 §2 Current Phase の head (コミット hash) を実機 (`jj log -r main` / `git log`) と照合する。**main が state 記録時より進んでいたら §継続作業指示は失効扱い** — 別セッションが消化した可能性が高い。失効時は指示を実行せず、実機確認の結果と次アクション候補の提示に降格する (他のセクションは背景知識として読んで良い)
3. **`loaded_by:` が空なら**: `state:` の実体を Read し、直後に `loaded_by:` へ 1 行追記する (`  - <ISO時刻> <自分の session-id>`)。以後この状態ファイルは自分のもの
4. **他セッションの記録が既にあるなら**: その状態ファイルはその系列に消費済み。自分のものとして採用せず、journal / メモリ / リポの実機確認から通常どおり立ち上がる (その系列はクラッシュしても `claude --continue` で続くため、状態はそちらが正)

> Why: 状態ファイルは「1 つの後継セッション」宛て。多重ロードすると 2 系列が同じ状態から分岐して同一 ws を取り合う。

## 継続作業指示 (§10 Recovery Notes 内) の扱い

`loaded_by:` を追記したら、§継続作業指示を出どころラベル (`[ユーザ 指示]` / `[AI 自律]` / ラベル無し) で分岐する。分岐の規則は `send` で受けた時と同じで、reference の `session-state/handoff` の「継続作業指示の扱い (ラベル分岐)」節を読んで従う。**`[AI 自律]` とラベル無しの項目は、確定裁定との矛盾を裏取りするまで実行しない**。

## 書く側の禁則

状態ファイルは、旧セッションが生きていられない時か相手を今起こせない時だけのフォールバックで、書く判断はユーザか hook の指示による (自主判断で書かない)。指示があればユーザに問い返さず書く。書く時は reference の `session-state/write` を読む。
