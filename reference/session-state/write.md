# セッション状態ファイルの書き方

`/clear` でセッションを捨てる前、または compaction で要約に潰される前に、後継 (あるいは要約後の自分) がゼロコンテキストから立ち上がるための状態ファイルを書く手順。

**kawaz または hook の明示指示でのみ書く**。区切りの良さ・context 残量・保険を理由に自発的に書かない (中断は `claude -c` で再開でき、context full でもダンプ経由で復帰できる)。

## 0. 前提チェック (clear 前のみ)

`/clear` は「区切り」でのみ行う。以下が汚れているなら、先に片付けるか compaction 側に倒す:

- 未コミット / 未 push の変更 (`jj status` / `git status`) — 残すなら理由と場所を明記する
- 走行中の worker・background task — 完了を待つか、状態を直列化しきれないなら compaction
- 進行中のユーザとの議論 (未決の論点) — 状態ファイルに論点として書けるなら clear 可
- **現コンテキストにしか無い永続知識** — §1 の永続化ファーストでリポ側へ落としてから書く

## 1. 永続化ファースト (状態ファイルを書く前に)

状態ファイルはロード 1 回で消費される揮発ハンドオフであり、**永続知識の置き場ではない**。書き始める前に、現コンテキストにしか無い以下をリポ側へ落とす (分類は reference の `docs-authoring/knowledge-timing`):

- 確立した手順・復旧手順 → `docs/runbooks/`
- 調査で確定した事実・数値 → `docs/findings/` / `docs/knowledge/`
- ハマり所と解決のペア → `docs/journal/`
- 未決の論点 → `docs/QUESTIONS.md` / `docs/issue/`

落とした後、状態ファイルからは**参照で指す** (本文を二重化しない)。この順序を守ると継続作業指示の多くが「`<doc>` を読んで実行」の 1 行になり、粒度の問題も同時に消える。

状態ファイルは cache に置く。消えても journal / メモリ / VCS 履歴から復元できる**運用状態だけ**を書く。

## 2. 保存先と命名

```
dir=${XDG_CACHE_HOME:-$HOME/.cache}/claude-session-state/<project-slug>/
```

- `<project-slug>` = **リポジトリのディレクトリ名そのまま** (例: `kuu` / `kuu.mbt` / `kuu-cli` はそれぞれ別ディレクトリ)。短縮・統合しない — 名前が前方一致する姉妹リポで「別リポのセッションが隣の状態を自分のものと誤認してロードする」事故を防ぐ。複数リポを統括するセッションは **cwd のリポ**の slug に置き、他リポの状態は本文 §2 Current Phase に書く
- 状態本文は `<YYYYMMDD-HHMM>.md` に書く (immutable、履歴として残る)
- `latest.md` は本文を持たないポインタ。**次節のテンプレをそのまま使う**

### latest.md のテンプレ

```
# このファイルは後継セッションが読むポインタ。状態の本文は state: の実体にある。
# repo: このハンドオフが管轄するリポの絶対パス (読む側は自分の cwd がこの配下かで照合する)
# state: 状態本文のファイル名 (同ディレクトリ、書き換えない)
# loaded_by: 引き継いだセッションの記録。空なら未消費。読む側が「  - <ISO時刻> <session-id>」を追記する
# この状態ファイルはユーザか hook の明示指示でしか書かない。書く指示が来たら
# ~/.local/share/repos/github.com/kawaz/claude-rules-personal/main/reference/session-state/write.md を読む。
repo: /abs/path/to/repos/github.com/<owner>/<repo>
state: <YYYYMMDD-HHMM>.md
loaded_by:
```

`loaded_by:` は空のまま書く (消費するのは読む側)。同一セッションが compaction 前に上書きする場合、既に自分の session-id が入っていればそのまま残す。

## 3. 内容 — 10 セクション

```
1. Active Plan          — 大目標と現在地 (1 段落)
2. Current Phase        — 各リポの head (コミット hash)・push/CI 状態・未コミットの有無
3. TaskList Summary     — 完了 / 残タスク
4. Session Decisions    — ユーザ裁定・設計確定を原文の要点で (DR / issue への参照付き)
5. Constraints/Blockers — 禁則 (安全制約は特に)・gate・運用ルール
6. Worker & Peer Topology — worker ハンドルは clear で失効するので「再 spawn 手順」として
                          書く (agent 定義名・使い分けの実績・委譲プロンプトの型)。
                          連携中の別セッション (ccmsg peer) は「sid + cwd + 交わした約束」
                          だけを列挙する — room 番号や aN は後継が room に参加していないので
                          使えない。後継は相手に「{cwd} の新セッションです、前任の約束を
                          引き継ぎます」と名乗って再接続する
7. Skills Invoked       — 使った skill と、その中で得た運用知見 (罠・定石)
8. Editing Files        — 主要ファイルと設計正本の所在。**意図的にリポ外へ置いた生成物**
                          (例: 業務 cwd を含むレポートを `~/.cache` へ) はパスと理由を
                          列挙する (後継が「消して良いか / 参照すべきか」を判断できるように)
9. Failed Attempts      — 試して駄目だった事と理由 (要約が残らないので厚く書く)
10. Recovery Notes      — 一次資料を読む順序 (立ち上げの最短経路)、Monitor / subscribe の
                          再起動要否、各 workspace の @ 位置。**§継続作業指示を必ず明示的
                          小節として立てる** — 「次セッションで即やる作業がある」「無いから
                          候補提示」のどちらかを断定する形で書く
```

文体はゼロコンテキストの初見読者向け (略語・セッション内の造語を持ち込まない)。

## 4. §継続作業指示の書式

各項目の先頭に**出どころラベルを必ず付ける** (読む側はラベルで分岐する):

- `[kawaz 指示]` — kawaz が明示的に指示・承認した作業。**根拠となる発言の要点を併記する** (例: 「kawaz『Release 出すところまでやって』2026-08-20」)
- `[AI 自律]` — このセッションの AI が自己判断で立てた作業。判断の根拠 (どの観測 / どの issue から導いたか) を併記する

判定に迷う項目は `[AI 自律]` にする。書く時点でその作業が**既存の DR / 裁定を覆すもの**だと気づいたら、継続作業指示に書かず `docs/QUESTIONS.md` の裁定待ちへ回す (AI が単独で裁定を撤回しない)。

**粒度**: 1 項目 = 1 検証可能単位 (完了をどう確認するかが 1 行で書ける粒度。reference の `delegation/orchestration-phases` Phase 0 と同じ基準)。複雑な手順は**具体的な実行コマンド例と結果の見方**まで書く — 省くと後継が手探りのやり直しをする。ただし手順そのものが再利用価値を持つなら §1 で runbook / findings に落とし、継続指示は「`docs/runbooks/<file>` を読んで実行」の参照形にする。

## 5. compaction 前に書く時の力点

compaction では不完全な自動要約が付いてくる。役割は「要約の補正レイヤ」なので、保存先・10 セクション・継続作業指示の書式は同じまま、次に厚く倒す。走行中の作業があっても書ける (むしろその時用)。

- **要約器が落とす精密情報の保険**:
  - 正確な識別子: コミット hash・ファイルパス・数値 (テスト数、台帳件数)・msg id
  - ユーザ裁定の**原文の要点** (要約の言い換えで意味が滑るのを防ぐ)
  - **安全制約・禁則** (例: 特定モデルの使用禁止) — 要約で消えると事故る筆頭
  - Failed Attempts (要約は成功物語に圧縮しがち)
  - **§継続作業指示** — 要約が「作業中の話題」として圧縮すると誤読の元。出どころラベル込みで原文の「次にやる作業」として明示保持する (要約はラベルを真っ先に落とす)
- **生きたハンドルの現在状態** (clear と逆でランタイムは生き残る):
  - worker が「どの ws で・何を持っていて・次の一手は何か」「未処理の指示があるか」
  - 走行中 Monitor / background task の一覧と、何を待っているか
  - 未コミット変更の所在と、誰がコミットする約束か
  - §6 Worker & Peer Topology は**ハンドル前提**で書いてよい (SendMessage 宛先はそのまま有効)

compaction 後の最初のターンで、自動注入は無いので `latest.md` 経由で状態を Read し直す (summary に言及が残るとは限らない — 状態ファイル側が正、summary は補助)。同一セッション内の再読なので `loaded_by:` の追記は要らない。§継続作業指示があれば、要約前に取り組んでいた作業が消えていないかを確認し、消えているならラベルで分岐して着手する (分岐は reference の `session-state/load` と同じ)。

## 6. 完了報告と自己 /clear または自己停止

**§10 Recovery Notes 内の §継続作業指示に何を書いたか (or 書かなかったか) を出どころラベル込みで報告に含める** — 後継が立ち上げ後に即実行する内容を kawaz が事前に把握でき、`[AI 自律]` 項目をこの時点で否認できるように。

その上で、**`$HYOUI_SESSION_ID` が設定されていれば `/clear` まで自分で実行する**。打つ内容は「kawaz が作業を続ける気があるか」で決める (継続作業指示の有無ではない):

```bash
# A. 作業を畳んで続ける (context full 等でリセットしたい雰囲気) → 引数付き /clear
hyoui input "$HYOUI_SESSION_ID" \
  'text:/clear ~/.cache/claude-session-state/<slug>/latest.md があれば reference の session-state/load の手順でロードし、継続指示があれば実行、無ければ次の優先作業候補を提案' \
  key:Enter

# B. 今日はここで終わり (「作業終了」「もう寝る」等) → ccmsg stop で自己停止
ccmsg stop "$CLAUDE_SESSION_ID"  # sid 不明なら ccmsg peers で自 sid を確認して渡す
```

- **A で引数を省かない**。素の `/clear` だと後継は SessionStart hook の指示 (role skill のロード等) を済ませただけで指示待ちに入り、状態ファイルを読まない (実機確認済み)。**引数には latest.md の絶対パスを必ず入れる** (`<slug>` を実際の値に展開する) — これが後継の唯一の起動トリガ。上の 1 文は継続作業指示の有無を両方カバーするので、有無で打ち分けない
- **B で `/clear` を打たない**。作業する気がないのに新規セッションが起き、role skill のロードで無駄に context を食う
- 引数に空白を含むので `text:...` 全体を quote する
- **A / B の判断がつかないときは注入しない**。保存先を提示して「続けるなら A、終わるなら B」と両方示して委ねる (誤って B を打つと作業続行の意思を潰す)
- **順序が本質**: 状態本文の書き込み → `latest.md` 更新 → 完了報告の本文 → 最後に `hyoui input`。注入された `/clear` はプロンプト行に乗り**現ターン終了直後に実行**されるため、これより後にやるつもりの作業は消える
- §0 の前提チェックが汚れたまま clear を見送った場合、kawaz が「保存だけ」と言った場合、`$HYOUI_SESSION_ID` が無い場合は注入しない (保存パスを提示して終える)
