# 蓄積系のデータレイク (ライブの置き場 + 日次・月次の Parquet + DuckDB で分析)

定期的な計測・ログ・イベントを溜め続け、後から推移を集計するデータの置き方。常駐プロセスを持たず、ファイルを並べるだけで、記録が増え続けても容量と読む時間が抑えられる形にする。

## 構成

```
<data_dir>/
  scans/<表>/<id>.parquet          # 1 回の記録 = 1 ファイル (ライブの層)
  daily/<表>/YYYY-MM-DD.parquet    # 終わった日の分を 1 ファイルにまとめたもの
  monthly/<表>/YYYY-MM.parquet     # 終わった月の日次を 1 ファイルにまとめたもの
  <名前>.lock                       # 排他用
```

- 一番上を層、その下を表で分ける。全期間は `read_parquet('<data_dir>/*/<表>/*.parquet')` の 1 本で読める。層ごとの量 (まとめ忘れが溜まっていないか) は `ls` で見える
- 過去分は 1 年あたり月次 12 ファイルになる。間引き (古いものを粗く残す) は要らない。全部の記録を残しても小さいので、間引きで情報を落とす理由が無い
- 表は 1 ファイル 1 表 (Parquet の制約)。表どうしは記録の id の列で結ぶ。どの表にも id の列を持たせる

## ライブの層

ライブの層は書き手の都合で選んでよい。分析は常に Parquet を読む。

- **1 回の書き込みが記録の最後に 1 回だけ** (定期計測のように、メモリで集計して最後に書く) なら、直接 `scans/` に Parquet を書く。途中で落ちても「その回の記録が無い」だけで、壊れた状態が残らない
- **少しずつ書き続ける** (イベントの追記) なら、ライブは SQLite や追記の JSONL にし、区切りで Parquet に書き出す。ただし読む側が「直近はライブの置き場、過去は Parquet」の 2 か所を読むことになり、境目の処理が要る。避けられるなら避ける

## まとめ方 (日次・月次)

- まとめる処理は別の定期ジョブにせず、**書き手の記録の最後**に「終わった日・終わった月があれば、まとめる」を足す。記録が毎日走るなら、月次は実質その月の最初の記録の時に走る
- 日・月の区切りはローカル時刻 (人が「何日の分」と読む単位、launchd の起動時刻もローカル)。記録の中の時刻は UTC で持つ
- 書き出しは zstd の強めの圧縮: `COPY (...) TO '<file>' (FORMAT parquet, COMPRESSION zstd, COMPRESSION_LEVEL 19)`

**ファイルの中の並べ方が大きさを決める。** 同じキー (パスなど) の行を隣に集め、その中を時刻の順に並べる (`ORDER BY <キー>, <id>`)。計測をまたいで値が変わらない行が多いデータでは、列ごとの圧縮 (辞書・差分) がそれを丸ごと畳む。

| 並べ方 (ディレクトリの大きさの記録、1 回 約 1.7 万行、170 回分) | 大きさ |
|---|---|
| SQLite (パス文字列は別表で 1 回だけ持つ形) | 約 1.1 GB (1 回 約 6.5 MB の実測を 170 回分に積算) |
| Parquet zstd 19、キーの順 | 2.8 MB |
| Parquet zstd 19、記録の順 | 16 MB |

## 落ちても壊れない手順

1. まとめたファイルを一時名 (`<name>.parquet.tmp`) で書く
2. fsync してから rename で正式な名前に置く
3. 元のファイルを消す

2 と 3 の間で落ちると、同じ記録が元のファイルとまとめたファイルの両方にある。**読む側は記録の id で重複を除く** (同じ id の行は中身も同じなので、どれか 1 ファイルの分を使う)。次のまとめ直しで二重にならないこと (まとめる対象に既存のまとめたファイルも入れて、id で重複を除いてから書く)。`.tmp` は読まない。

## 記録の id

連番の採番元 (DB の autoincrement) が無いので、**ファイルを読まずに一意に決まるもの**にする。記録の開始時刻 (UTC の unix 秒) を使い、前に払い出した id 以下になる時は「前の id + 1」にする (同じ秒に続けて記録すると重なる)。前に払い出した id は、書き手の排他用のロックファイルの中身に持つ。

## 排他

- **書き手どうし**: 記録とまとめ直しの全体を 1 つのロック (`flock`) の中で行う。2 つ目の書き手は待たずにエラーで終わる (定期実行が重なった時、後の回は飛ばしてよい)
- **元のファイルを消す操作と読み手**: 読み手がファイルを列挙してから開くまでの間に、まとめ直しが元を消すと読み手が失敗する。消す操作は排他ロック、読み手は共有ロックを取る。ロックを取れない読み手 (ブラウザから HTTP で読む等) は、列挙と取得の間に消えたファイルの 404 で一覧を取り直してやり直す

## 列の足し方

列は名前で読む (`read_parquet(..., union_by_name = true)`)。列を足しても古いファイルはそのまま読め、無い列は NULL になる。schema の版を持たなくてよい。列の意味を変える・消す時は、新しい名前の列を足す。

## DuckDB をどう持つか

- 書き手が Rust なら `duckdb` crate (`features = ["bundled", "parquet"]`)。書き出し・まとめ直し・集計を同じ SQL で書ける。代わりにバイナリが約 45 MB 増え、依存を最初からビルドすると数分かかる。`parquet` / `arrow` crate で書けばバイナリは小さいが、まとめ直しの重複除去と並べ替えを自前で書くことになる
- 拡張の自動読み込み・自動インストールは切る (`autoinstall_known_extensions = false`、`autoload_known_extensions = false`)。Parquet は組み込み
- まとめ直しで zstd 19 を使うと CPU を食うので、低優先度で走るジョブではスレッド数を 1 に絞る (`SET threads = 1`)
- 分析は手元の `duckdb` CLI か、ブラウザの DuckDB-WASM で、同じ `read_parquet` の SQL を書く
