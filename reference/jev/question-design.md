# Jev の質問の立て方

TypeSafe AI の判断専用 API Jev (`POST https://api.typesafe.ai/v1/systemone`) に送る質問 (`questions`) の組み方。1 つの request は 1 つの `state` に対して複数の質問を並列に評価し、質問ごとに型付きの答えを返す。

## 型は答えの構造から決める

後段のコードがどんな値を必要とするかを先に決め、そこから型を選ぶ。質問文の見た目からは選ばない。

| 答えの構造 | 型 | 返る値 | コード側の使い方 |
|---|---|---|---|
| 順序の無い有限の候補から 1 つ (名義尺度) | `choice` | `choice`, `probabilities`, `confidence` | ラベルで分岐 (`switch`) |
| 順序のある段階のどこか (順序尺度) | `score` | `score` (level の間も取る), `legend`, `probabilities`, `confidence` | 閾値で比較 |
| 1 つの命題が成り立つか | `noul` | `noul` (yes の確率 0〜1) | 閾値で `if` |
| 画像の中のどこか (jev-1.14.0 以降、実験機能) | `box` | `box` (`top` / `bottom` / `left` / `right` を画像の幅・高さに対する比で), `confidence` | 座標として使う |

- 「担当部署」「言語名」「製品カテゴリ」は Choice。「深刻度」「緊急度」「経験の深さ」は Score。候補を列挙できるかではなく、候補の間に順序があり、その順序をコードが使うかで分ける
- 程度を Noul で聞かない。「Python が強いか」の Noul 0.5 は「中くらいに強い」ではなく「yes と no が半々」。程度が欲しいなら level を言葉で定義した Score にする
- 迷ったら、コードがそのまま行動に移せる方を選ぶ (Choice は分岐、Score は閾値、Noul は `if`)

## 1 問 1 論点、複合的な判断は分解してコードで合成する

1 つの質問には、詳しい人が 1 秒で判断できる 1 つの論点だけを入れる。「このコードは良いか」「この依頼を総合評価せよ」は聞かない。

- 複数の要因で決まる判断は要因ごとの質問に割り、重み付けや組み合わせはコード側に置く。重みを変えたい時はコードを直せばよく、質問文を書き換えずに済む
- 「怒っていて、かつ返金を求めているか」のような 2 条件の Noul は 2 問に割って `and` をコードで取る
- 価値判断・リスク選好 (「閉め出しは開けっぱなしより悪い」「安全な方を選べ」) を質問に入れない。事実の問い (誰か家にいるか、鍵を持っているか) に分解し、どちらを優先するかはコードで決める
- 前段の答えがないと後段の request を組めない時 (答えで state に足すデータを取りに行く、次の選択肢を決める) だけ 2 段にする。それ以外は全部 1 request に入れる

## 同じ state への質問は 1 request にまとめる

質問は並列に評価され、数を増やしても応答時間はほとんど変わらない。費用は足した質問文の token だけ。

- 使うか分からない質問も込みで全部送り、コードが要る答えだけ拾う (speculative fan-out)。例: 部署の Choice と、部署が returns の時だけ使う返品理由の Choice を一緒に送る
- 質問数そのものに上限は無い。上限は token (request あたり 64k、state + 質問 1 件で 32k)。入りきらなければ同じ state で request を分ける
- 1 つの答えは他の質問の文脈にならない。質問を足し引きしても他の答えは変わらない

## Noul の書き方

- 高い値が yes になる向きで書く。「個人情報を含むか」は良く、「個人情報を含まないか」は向きが逆で、`criteria` の true が「無い」側を指すような食い違いは精度が落ちる
- 疑問文でも平叙文 (「`message` は返金を求めている」) でもよい
- yes と no の境界が微妙な時は `criteria` に `{"true": "...", "false": "..."}` を入れ子で書く。`true` / `false` を質問の直下に置くと 200 が返るのに黙って捨てられる。`criteria` が要らない Noul も多いので、有りと無しを自分のデータで比べて良い方を残す
- 「該当するものを数える」は数えさせず、候補ごとに Noul を 1 問ずつ立ててコードで足す

## Choice の書き方

- Choice は必ずどれかを選ぶ。範囲外の入力 (無関係な文、意味の無い文字列) にも 0.5〜0.98 の確率で何かを選ぶので、入力が候補の外に出うるなら受け皿を付ける:
  - **companion Noul** (推し): 同じ request に「`message` は `products` のどれかについての話か」の Noul を足し、Noul が明確に yes の時だけ Choice を読む。範囲の境界を `criteria` の true / false で具体的に書け、Choice の確率は本物の選択肢の間だけで分かれる。Noul が中間帯なら人に回す
  - **`none` の選択肢**: 最小の変更で、くっきり範囲外の入力は `none` 1.00 になる。半分だけ範囲内の入力では `none` と本物の選択肢で確率が割れ、どちらの値も行動の根拠にしにくい
  - 複数の選択肢に同時に当てはまりうるなら、Choice をやめて選択肢ごとの Noul にする (全部低ければ範囲外)
- 選択肢名 (`criteria` のキー) はモデルに送られる。名前と説明で選択肢同士の境界が分かるように書く。似た 2 つが取り違えられる時は、説明をオブジェクトにして `what` / `not_for` / `examples` のように「何を含み、何は隣の選択肢か」を書く (キー名は自由で予約語は無い)
- 説明は `null` でもよい (名前だけで分かる選択肢)
- 先頭の選択肢に寄ることがある。大事な判定は選択肢の順序を入れ替えて答えが揺れないか確かめる
- 選択肢は 255 個まで。足すコストは数 token なので、絞った候補ではなく全リストを渡す
- 深い分類木は 1 段ずつ Choice を問い、各選択肢の値にその下の部分木を入れて、コードで木を降りる
- 抽出 (日付・金額・メールアドレス) は生成させない。正規表現や生成モデルで候補を作り、どれが正しいかを Choice で選ばせる。日付は年・月・日をそれぞれ Choice (「書かれていない」の選択肢付き) で取り、比較や計算はコードでする

## Score の書き方

- `criteria` は低い方から高い方へ並べた level の説明の配列 (2〜10 段。11 段以上は 400)。配列の位置が level 番号 (0 始まり)
- 各 level は単独で state と照らされる。level の説明だけで、その段に当たる状況が分かるように書く。例が要るならオブジェクトにして説明と例を分ける
- `score` は level 番号 × 確率の和で、level の間の値を取る。閾値を超えたかの判定には使ってよいが、level の間の量 (「2.4 だから 4 割増し」) を補間しない

## 質問 ID と instructions

- 質問 ID (`questions` のキー) はモデルに送られない。答えを受け取るキーにだけ使われる。意味のある名前を付けてよいが、ID で察してもらうことはできないので、問いは全部 `instructions` に書く
- `instructions` / 各 `criteria` は文字列・オブジェクト・配列・`null` を取る。まず文字列で書き、比べる対象のデータを添える時 (`{"question": "...", "compare": [...], "focus": "..."}`) や、コードで組み立てる時にオブジェクトにする
- 質問文と `criteria` は英語で書く。日本語の state をそのまま渡してよいが、質問文を日本語にすると Noul が大きく動く (CJK の扱いは reference の `jev/request-and-state`)
- 字面どおりに読まれる。否定・範囲の語・暗黙の条件は書いたとおりに解釈されるので、境界の事例は `criteria` に書く。間違った答えを見て「本当はこういう意味だった」と説明したくなったら、その説明が instructions に足りない半分
- 計算・日付の前後比較・数を数えることはさせない (コードでする)。16 進の色のような数値表現より名前 (「赤」) の方が当たる
