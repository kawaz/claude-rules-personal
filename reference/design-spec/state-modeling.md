# 状態のモデリング — enum に押し込めず、問いに答えるフィールドを決める手順

契約や API で「状態」を表すフィールドを決める・見直す時の手順 (1 件の設計作業で迷走した経験から起こしたもので、確立した工学のノウハウではない。合わない場面では目的の側を優先する)。1 つの enum に複数の軸を押し込めると、新しい状況が出るたびに値を足しては組み合わせが破綻する。逆に軸を分けることに気を取られると、使い道の無い変数に名前を付けて既存フィールドと重複する。どちらにも流れないための順序。

## 手順

1. **答えるべき問いから始める**。利用者 (client / 他コンポーネント / 人) が何を判断したいかを列挙する (例: プロセスは何個あるか、この値は信じてよいか、どう開くか)。状態の名前や enum の値から始めない
2. **既存フィールドの棚卸しを先にやる**。各問いを既存フィールドで答えられないか当てる。答えられる問いには何も足さない (「軸を分ける」つもりで既に軸になっているフィールドを見落とすのが典型の迷走)
3. 残った問いにだけフィールドを足す。名前は **答える問いの側の語彙** で付ける (仕組みの名前でなく、利用者がその値で何を判断するかの名前)。従属関係 (どのフィールドが無い時に意味を持たないか) を各行に書く
4. 導出値 (computed) は **使う場所を名指しできるものだけ** 残す。使う場所が言えなければ消す。残すものは線上に載せず、共有実装 1 箇所 (契約パッケージの関数など) に置いて全員が同じものを呼ぶ (導出のずれを線上のフィールドで解こうとしない)
5. 表は 3 つに分けて書く: (a) 観測されるフィールドと従属、(b) 導出と使う場所、(c) できること (フィールドの条件で書く)。(a) と (c) を混ぜない
6. 判定表の目的は **全部の組み合わせを洗い出して、何に注目すべきかが見える形で俯瞰する**こと。大きなマトリクスになってよい。書式は目的が叶えば何でもよいが、セルに単一値 (複数値が入るなら列が足りないので列を割る)、判定に使う条件は ⭐、無関係は空欄、値が無いのは none、true / false は ✅ / ❌、が読みやすかった
7. 主語が違えば行を分ける (サーバが観測する値と、client が受け取った応答の有無・可否は別のフィールド)
8. 1 つの enum が 2 つ以上の軸を表していたら分割する。互換性や影響範囲は分割しない理由にならない (`design-priority` rule)

## 迷走の兆候

- 「状態 X を足すには enum のどこに入れるか」で悩んでいる → 軸が混ざっている (8)
- 変数に名前を付けたが、それを読む側のコードや画面を言えない → 消す (4)
- 判定表と機能表が 1 つになっていて、セルに「○ (ただし…)」が並ぶ → 分ける (5)、列を割る (6)
- 新しい変数が、既存フィールドの言い換えになっている → 棚卸しに戻る (2)
