# 設計文書の着手前チェック

設計文書 (DR / プロトコル / 仕様) を書き始める前と、決めていく途中で確認すること。

前提となる書き方の思想 — 目的を手段に汚染されない形で書く、手順の量から目的を逆算しない、何を増やしたくないかを目的と同格に置く、論点は「誰の責務か」から問い責務外は境界の記述として残す — は `for-all/rules/design-thinking.md` が正本。以下はその上で個別に確認する項目。

## 着手前に固めること

### スコープの粒度を決める

目的は粒度に紐づく。粒度が定まらないと目的が書けない。

「システムを安全にする」は粒度が大きすぎて、権限分離も暗号化も全部入ってくる。絞ることで初めて外側を切り出せる。

### 前提条件を列挙し、満たさない場合を併記する

「満たさない場合どうなるか」を書くと、それが本当に前提なのか、単に自分が要求しているだけなのかが判別できる。後者なら、他者の責務を自分の要求として書いている疑いがある。

前提条件が増えていくときは、境界の引き方を疑うこと。責務の範囲が曖昧なままだと、他者の責務を自分の要求として書いてしまう。

## 決めるときに守ること

### 実装に裁量を残してよい箇所とそうでない箇所を区別する

複数の実装が同一の結論に達する必要がある箇所は、仕様側で規則を固定する。何でもよいが一つに決める、が正しい。裁量に残すと、双方が異なる結論を出して壊れる。

結論が一致する必要がない箇所は、意図だけを規定して形式は任せる。URL の形やメッセージフォーマットなど。要件は性質として書く。

この区別を誤ると、規定すべきを曖昧にし、任せるべきを縛る。

### 曖昧な数値を書かない

「適切な値」「過大でない」と書くのは、決めるべきことを実装に投げている。推奨値と根拠を書く。根拠があれば、状況が違う実装者が自分で調整できる。

### やらないことを、理由と目的への紐づけとともに書く

理由なしの禁止は制約に見え、後の人が回避したくなる。「目的の後段に反する」のように参照先を書いてあれば、追加を検討した人は「では目的のほうを見直すべきか」という正しい問いに着地する。目的が変わったなら追加は正当なので、判断が上のレイヤに上がるだけで、間違った追加にはならない。

不採用にした選択肢は表として残す (書式の規範は `for-all/rules/document-design-rationale.md`)。実装者が思いつきうる近道は、明示的に潰しておく。

### 機能を足して管理が減るなら、進む方向は合っている

通常は逆になる。噛み合っている設計では、要素を足したことで別の要素が不要になることがある。そういう噛み合いが出るなら、目的と手段が一致している。

### やらないことに反する変更を検出するテストを書く

文章は読まれないことがあるが、CI は必ず読まれる。設計の核が「持たない」「増やさない」という形をしているとき、それを壊す変更は改善に見えるため、文章の禁止では止まらない。核が保たれていることをテストにしておく (観点の立て方は reference の `testing/test-coverage-checklist`)。
