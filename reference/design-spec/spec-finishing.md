# 設計文書の仕上げチェック

一通り書き終えた後、あるいは指摘対応が一巡した後に確認すること。

## 全体を通読する

指摘のたびに該当箇所だけ直すと、残骸が残る。前提が変わった後も古い記述が生き残り、文書内で矛盾する。個別対応を数回続けたら、一度通しで読む。

## 目的が確定する前に書いた部分を疑う

目的が後から明確になった場合、それ以前の記述はすべて別の前提で書かれている。特に、代替案の評価や前提条件は書き直しが要る。

## 相互参照を機械的に検証する

節番号の参照は、節を追加・移動するたびに壊れる。手で追わない。

```python
heads = set(re.findall(r'^#{2,3} (\d+(?:\.\d+)?)\.? ', s, re.M))
refs  = set(re.findall(r'§(\d+(?:\.\d+)?)', s))
print(sorted(refs - heads))
```

## 廃止したものへの言及自体を消す

方針を変えたとき、「なぜ旧案を採らないか」を本文に書き足したくなる。自分の判断を正当化したくなるためだが、読み手には存在しない選択肢の否定を読まされるだけである。

消す。不採用の記録が要るなら、末尾の不採用表に一行だけ残す。本文中に残す理由はない (禁則の正本は `for-all/rules/no-historical-noise.md`)。

これは頻出する。手直しを重ねるほど、廃止済みの前提に基づく記述が本文に堆積していく。通読時に最も多く見つかるのがこれ。

## 章立ての順序と分量のバランスを確認する

思いついた順に書き足していくと、文書は追記順のまま積み上がる。前半に問題提起がないのに結論めいた記述が現れる、といった構成になり、そのまま放置されやすい。

読む順序で並んでいるかを見る。前提のない結論、参照先が後ろにある説明、この時点では判断できない選択肢の提示があれば、位置が違う。

分量の偏りも手がかりになる。ある節だけが突出して長いなら、そこに複数の主題が混ざっているか、他が書き足りない。逆に一行しかない節は、他に統合できることが多い。

## 削って良くなるかを試す

説明が 3 箇所に分散していたら 1 箇所にまとめる。不採用の話が本文中央にあったら末尾に移す。削ると目的が効くようになることが多い。

## 全文を規範と照らし合わせる

修正が一巡したら、最新の理解のうえで全文を本規範 (着手前チェックを含む) と突き合わせる。個別の指摘に対応している間は視野が局所化しており、規範に反する箇所が残る。

## 作業上の注意

### 宣言と実行を混同しない

「直します」と書いて手を動かさずに終える、が起こりうる。作業を伴う結論を出したら、その場で実行する (統括としての正本は reference の `delegation/main-role-playbook`)。

### バージョン管理のない環境では版を残す

VCS 下ならこの節は不要。そうでない環境 (チャット、一時的な作業ディレクトリなど) では、修正で悪化したときに戻す手段がないため、書き換える前に旧版を別ファイルとして残す。
