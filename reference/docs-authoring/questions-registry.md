# 裁定・確認待ちは docs/QUESTIONS.md に常時集約

プロジェクト内の `docs/QUESTIONS.md` に、ユーザの判断が要る項目を集約する。

**AskUserQuestion は使用禁止** (タイムアウト無しで無限待ち、リモート応答不可、ユーザ入力中の割り込みが不快)。判断が要る時はチャット本文で尋ね (自由文回答歓迎)、裁定を待つ間に他の作業へ進められるなら本ファイルに 👺ラベル付きで起票して参照する。

起票するのは **メインコンテキストだけ**。ユーザと直接コミュニケーションを取るのがメインだからで、ワーカーは AskUserQuestion も QUESTIONS.md への起票も行わない (判断が要る点は委譲元への報告に含めて返す)。

ここに書くのは一般規約で、業務 overlay 側はこれを土台に差分ルールを重ねる (例: ファイル名・commit 有無・スコープを差し替える)。

## Why

- ユーザが「何待ちか」をチャット履歴から掘り返す手間の削減
- AI にリストと説明を再生成させるコストの削減 (今何待ち? を撲滅)
- 実装完了や質問提起が散発的に発生して TL に流れてしまい、未確認のまま亡失される問題を、本ファイルが解決する
- セッション境界・並行セッションを越えて裁定・確認キューが共有される

## テンプレート

`docs/QUESTIONS.md` が無い / 空のときは `~/.local/share/repos/github.com/kawaz/claude-rules-personal/main/reference/docs-authoring/templates/QUESTIONS.template.md` をそのままコピーして使う (運用規約は当該ファイルの `<details>` 節が正本)。

## 統括固有の観点

- **Q は意味論から書く**: 「(a) 暫定 vs (b) 他候補 vs (c) 保留」でなく、原意図 / 選択肢の意味論的な違い / 統括推しの根拠を明示 (worker 観察のラベル貼りで並べるのは reference の `delegation/main-role-playbook` が挙げる失敗パターン)
- **C は「何を見れば済むか」を絞ってから出す**: 実装完了を丸ごと投げるのでなく、確認すべき対象と観点を絞る (= 自分で観測できることは全部やってから残りを出す、`empirical-verification` rule の「検証しきった後の振る舞い」)
- **裁定でないものを裁定として投げない**: 着手順・作業の可否など自分で決められることは起票せず進める (統括の自律進行)
- 複数論点が絡む Q は α/β/γ 分割 (独立軸に分ける)
