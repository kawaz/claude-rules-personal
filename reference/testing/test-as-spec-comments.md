# テストコード = 真の仕様書 (コメント inline 化)

> 各テストケースは何をテストしているのか意図や判断をテストケースのコメントに込める。DR は議論ログとして今もあるが、それをテストケースにも適用しておくと、テストが仕様であると言う形に出来る。理想的には完璧なテストセットがあれば言語移植も簡単だし、リファクタやサイズ最適やパフォーマンス最適も安心して出来るし性能向上にもつながる。完璧に同じ振る舞いが定義できていればソースコードがなくてもゼロから再現ができるのが理想。

**核**: テストコード = 真の仕様書。**「なぜこの入力か」「なぜこの期待結果か」「どの DR の判断に基づくか」をテストケース直近のコメントに込める**。

これにより:

- ソースコードを捨てても test だけで実装をゼロから再現可能
- 別言語移植も test を pass させれば済む
- リファクタ / 最適化 / 性能改善も test 全 pass で safety 確保
- 後続セッション / 別エンジニアが test を読むだけで仕様 + 判断経緯を理解可能 (= DR を別タブで開かなくて済む)

## コメント様式 (= 推奨パターン)

- **全 case に意図コメントを書く (= 「自明だから省く」は禁則)**: プロジェクトに浸かった立場の自明はゼロコンテキスト読者 (= 別言語移植者 / OSS 公開での初見 / 半年後の自分) には自明でない。例えば `parse_duration("5m") -> Duration(300000)` は ms 換算規約 + `m=分` の単位規約が暗黙に効いていて、明文化されないと再現できない。コメント省略の禁則であって、test 自体の取捨 (= reference の `testing/test-coverage-checklist` の「対極」) とは別の話。迷ったら書く (= 過剰コメントより省略の方がリスクが高い)。
- ケース直前に意図を書く: 「**何の入力で何を確認、なぜそうなるべきか (= DR / 仕様根拠)**」。長さは説明に必要なだけ — 単純な case は 1 行、複雑な条件 / 境界判断 / 仕様根拠の絡む case は段落で書いて構わない (= 行数を絞るために必要な説明を削るのは本末転倒)。
- 複数 case をまとめた section の冒頭に共通の判断を書く (= 軸の意味論)
- **DR の判断本質を文章で書き、DR ref は補助 marker**: 「`// 末尾 @ も先頭 @ と同等に Absolute フラグ立てる: @ idempotent 規約による (DR-0007 Phase 2 marker)`」のように、test 読者が **DR を別タブで開かなくても判断が完全に分かる** 形にする。`// DR-0006: -n is cat-equivalent` のような DR ref 単独引用は不可 (= DR が消えた / 別プロジェクトに移植 / OSS 公開した時に意味を失う)。**portability の根拠**: 「テスト = 真の仕様書、ソースを捨てても再現可能、別言語移植も test を pass させれば済む」を満たすため、test 内の reference は test 単体で self-contained でなくてはいけない。DR ref は「この判断は記録された経緯がある」という意図的な history pointer 扱いで、必須ではなく補助情報。同じ原則は issue ref / PR ref / commit hash 等の全 cross-reference に適用
- 境界判断は **なぜそこが境界か** を明示 (例: `// 6 ASCII whitespace bytes only — Unicode WS (NBSP, U+2028) intentionally not trimmed per DR-0001`)
- 仕様変更で test を変える時、**変更の議論ログも近接 comment に追記** (例: `// DR-0005 で --eol 廃止に伴い -n の意味を cat 同等に refine`)

## Why

コメント inline により DR を別タブで開く必要がなくなり、test を読むだけで仕様 + 判断経緯が理解可能になる。テストが仕様の完全な表現になれば、実装は差し替え可能な従属物になる。
