# 暗号と鍵管理の用語集

## 用語の地図

ここに並べる用語は、「鍵をどう作るか」「データをどう守るか」「鍵をどう配り、どう信頼するか」「鍵をどこに置くか」の4つの問いのどれかに答えるための道具です。各用語は次の7項目で説明します。

- **何か**: 一言での定義
- **目的**: 何のために使うか
- **仕組み**: どう動くかの要点
- **保証**: これを使うと何が言えるようになるか
- **守るもの**: 何を何から守るか
- **SPOF・弱点**: これが破られる、または失われると何が起きるか
- **推奨**: 選択肢がある用語で、新規開発なら何を選ぶか、その根拠

同じカテゴリに複数の方式がある場合は、推奨する方式を先に書きます。新規では選ぶ理由のない旧方式は「従(旧方式)」と見出しに付け、その後ろに置きます。既存ツールを読むときに出会うので残していますが、cw では検討不要です。

推奨、他製品の採用方式、OS やブラウザの対応は、外部の情勢で変わります。「選定判断基準日」を添えた記述は、日付が古ければ一次資料で確かめ直します。

| 問い | カテゴリ |
| --- | --- |
| 鍵をどう作るか | 鍵の導出 |
| データをどう守るか | 共通鍵暗号と完全性、鍵の包み方 |
| 鍵をどう配り、どう信頼するか | 公開鍵暗号と署名、鍵の表現と信頼、パスワード認証プロトコル、FIDO |
| 鍵をどこに置くか | ハードウェアによる保護、実装上の概念 |

## 鍵の導出

鍵の導出は、パスワードや乱数のような「元の秘密」から、暗号に使える固定長の鍵を作る工程です。新規開発では、人が覚える秘密には Argon2id、すでに十分ランダムな秘密には HKDF を使えば迷う余地はありません。

### KDF(Key Derivation Function、鍵導出関数)

- **何か**: 入力の秘密から、指定した長さの鍵を作る関数の総称。下の Argon2id や HKDF はその具体例。
- **目的**: 形も強さもまちまちな秘密を、暗号がそのまま使える「均一でランダムな鍵」に変える。
- **仕組み**: 大きく2種類ある。① パスワード用 KDF は、わざと遅く重く作り、推測1回あたりのコストを上げる(Argon2id、PBKDF2、bcrypt)。② 鍵素材用 KDF は速く、ランダムな入力を用途別の鍵に分ける(HKDF)。
- **保証**: 同じ入力と salt からは同じ鍵が出る。出力から入力は逆算できない。
- **守るもの**: 元の秘密。
- **SPOF・弱点**: 2種類を取り違えると壊れる。パスワードに HKDF を使えば総当たりが一瞬で済み、ランダムな鍵に Argon2id を使えば無駄に遅いだけ。
- **推奨**: パスワード由来なら Argon2id、それ以外は HKDF-SHA256。

### CSPRNG(暗号論的擬似乱数生成器)

- **何か**: 予測できない乱数を作る生成器。OS の `getrandom` や `SecRandomCopyBytes` など。
- **目的**: 鍵、nonce、salt を作る。
- **仕組み**: OS がハードウェアのノイズなどを集め、暗号的に安全な方式で引き伸ばす。
- **保証**: 出力から過去や未来の出力を推測できない。
- **守るもの**: すべての鍵の予測不能性。
- **SPOF・弱点**: ここが壊れると、上に積んだすべての暗号が無意味になる。
- **推奨**: OS の乱数(Rust なら `getrandom` か `rand::rngs::OsRng`)。自前の乱数や `rand()` は使わない。

### salt

- **何か**: KDF に混ぜる、秘密ではないランダム値。
- **目的**: 同じパスワードから同じ鍵ができないようにする。
- **仕組み**: ユーザーやスロットごとに CSPRNG で作り、暗号文の横に平文で保存する。
- **保証**: 事前計算した辞書(レインボーテーブル)が使えない。1人分の総当たりが他人には流用できない。
- **守るもの**: 総当たりの効率化から、パスワード由来の鍵を守る。
- **SPOF・弱点**: 秘密ではないので漏れても問題ない。消えると鍵を再導出できないので、データと一緒に保存する。
- **推奨**: 16バイト以上のランダム値を、パスワードを設定・変更するたびに新しく作る。同じ鍵を導出し直すときは、保存してある salt をそのまま使う。

### Argon2id

- **何か**: 2015年の Password Hashing Competition の優勝方式で、現在の推奨パスワード KDF(RFC 9106)。
- **目的**: パスワードから鍵を作るとき、計算とメモリの両方を重くする。
- **仕組み**: 指定したサイズのメモリを埋め、何度も読み書きする。メモリ量、反復回数、並列度を調整できる。
- **保証**: 推測1回ごとに大量のメモリが要るので、GPU や ASIC で並列化しにくい。
- **守るもの**: 弱いパスワード由来の鍵を、オフライン総当たりから守る。
- **SPOF・弱点**: パラメータが弱いと効果が薄い。
- **推奨**: パスワード KDF はこれ一択。Argon2 には d と i もあるが、両者の長所を併せ持つ id を選ぶ。パラメータは RFC 9106 の第2推奨(64MiB、3回、並列4)を下限の目安とし、データと一緒に保存して後から強化できるようにする。cw はパスフレーズ入力の頻度が低いので、もっと重くしてよい。**パスワード KDF 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)

### HKDF(HMAC-based Key Derivation Function)

- **何か**: HMAC を使った「抽出と展開」の KDF(RFC 5869)。
- **目的**: すでに十分ランダムな秘密から、用途別の鍵を複数作る。複数の秘密を1つの鍵にまとめる。
- **仕組み**: Extract で入力を均一な擬似乱数鍵にし、Expand で `info`(用途ラベル)ごとに必要な長さの鍵を作る。
- **保証**: `info` が違えば、出力は互いに独立とみなせる(ドメイン分離)。
- **守るもの**: 1つの秘密を複数の用途で使い回したときに、ある用途の鍵から別の用途の鍵が推測されることを防ぐ。
- **SPOF・弱点**: 遅くないので、パスワードの直接入力には使えない。入力全体のエントロピーが低ければ、出力も弱い。
- **推奨**: HKDF-SHA256。`info` には「アプリ名、版、用途」を入れる(例: `cw/v1/slot/passkey`)。

### 従(旧方式): PBKDF2(Password-Based Key Derivation Function 2)

- **何か**: HMAC を何十万回も繰り返す、古典的なパスワード KDF。
- **目的**: パスワードから鍵を作るとき、1回の試行を重くする。
- **仕組み**: HMAC-SHA256 を反復回数ぶん連鎖させる。1Password は 65万回。Bitwarden は、暗号化の version 1 のアカウント(2026年11月より前に作られたもの)が 60万回で、それ以降に作られる version 2 のアカウントは Argon2id(6回、32MiB)が既定。**他製品の採用方式 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)
- **保証**: 1回の推測に一定の計算時間がかかる。
- **守るもの**: 弱いパスワードを、オフライン総当たりから守る。
- **SPOF・弱点**: メモリを使わないので、GPU や専用ハードで並列化されやすい。
- **推奨**: 新規では選ばない。FIPS 準拠が必須の場合だけ残る選択肢で、その場合は OWASP の目安(SHA-256 で 60万回以上)に従う。

### 従(旧方式): bcrypt

- **何か**: Blowfish 暗号の鍵スケジュールを利用したパスワードハッシュ。
- **目的**: PBKDF2 と同じく、推測を重くする。
- **仕組み**: コスト係数 n で 2ⁿ 回の重い鍵セットアップを行う。少量のメモリ(4KB)を使う。
- **保証**: PBKDF2 より GPU で効率化しにくい。
- **守るもの**: パスワード由来の鍵やハッシュ。
- **SPOF・弱点**: 入力は72バイトで切り捨てられる。メモリ使用量は Argon2 に比べて小さい。
- **推奨**: 新規では選ばない。Argon2id を使う。

## 共通鍵暗号と完全性

暗号化だけでは「読めないこと」しか保証されず、「書き換えられていないこと」は保証されません。新規開発では AEAD を使うのが前提で、方式は AES-256-GCM か XChaCha20-Poly1305 のどちらかです。cw は HPKE 経由で使うので、nonce を自分で管理する場面はほぼありません。

### AES(Advanced Encryption Standard)

- **何か**: 世界標準のブロック暗号。16バイト単位で、鍵長は 128/192/256bit。
- **目的**: データを、同じ鍵を持つ者だけが読める形にする。
- **仕組み**: 単体では16バイトしか扱えないので、GCM などの「モード」と組み合わせて使う。
- **保証**: 鍵がなければ平文が分からない(機密性)。
- **守るもの**: データの中身。
- **SPOF・弱点**: 鍵そのもの。また、モードの選び方と使い方を間違えると簡単に壊れる。
- **推奨**: 鍵長は 256bit 一択。128bit も現時点で安全だが、量子計算機(Grover のアルゴリズム)に対する余裕が大きく、AES 命令のある CPU(Apple Silicon を含む)では速度差もほぼない。192bit は実用上ほとんど使われない。この余裕が効くのは共通鍵の部分だけで、鍵を X25519 や P-256 で配っているなら、量子計算機に対する強さは公開鍵暗号の側で決まる(「公開鍵暗号と署名」の HPKE)。

### AEAD(認証付き暗号)

- **何か**: 暗号化と改ざん検知を一体にした方式の総称。
- **目的**: 組み立てミスの余地をなくし、機密性と完全性を一度に得る。
- **仕組み**: 鍵、nonce、平文、AAD を入れると、暗号文と認証タグが出る。復号時にタグが合わなければ失敗する。
- **保証**: 機密性、完全性、AAD との結びつき。
- **守るもの**: データの中身と、その改ざん。
- **SPOF・弱点**: 同じ鍵で nonce を再利用すると壊れる。削除や古い版への巻き戻しは検知できない。
- **推奨**: 共通鍵暗号は必ず AEAD で使う。方式は下の2つから選ぶ。**AEAD 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)

### AES-GCM(Galois/Counter Mode)

- **何か**: AES のカウンタモード(CTR)と GHASH を組み合わせた AEAD。CTR は、nonce に1ずつ増えるカウンタを付けた値を AES で暗号化して鍵ストリームを作り、平文と XOR する使い方で、AES をストリーム暗号のように使う(ChaCha20 と同じ形)。GHASH は改ざん検知用の MAC。
- **目的**: 高速な AEAD。多くの CPU にハードウェア命令がある。
- **仕組み**: 12バイトの nonce を使う。1Password と Proton Pass が使用。
- **保証**: AEAD の保証すべて。
- **守るもの**: データの中身と改ざん。
- **SPOF・弱点**: nonce の再利用は致命的で、認証用の内部鍵が漏れ、偽造もできるようになる。ランダムな nonce では、1つの鍵で暗号化できる回数に上限がある(12バイト全部を乱数にしたときの目安が 2³² 回。乱数の部分がそれより短ければ、上限はもっと小さい)。
- **推奨**: AES-256-GCM。他システムとの互換や FIPS が必要なときの第一候補。nonce の扱いは下の「nonce / IV」の安全パターンに従う。

### ChaCha20-Poly1305 / XChaCha20-Poly1305

- **何か**: 暗号化を担うストリーム暗号 ChaCha20 と、改ざん検知を担う MAC の Poly1305 を組み合わせた AEAD(RFC 8439)。どちらも Daniel J. Bernstein の設計で、ChaCha20 は Salsa20 を改良した20ラウンドの暗号、Poly1305 は1つの鍵を1回だけ使う前提の MAC。
- **目的**: AES 命令がない環境でも速く、定数時間で実装しやすい AEAD。
- **仕組み**: ChaCha20 は鍵(256bit)、nonce、ブロックカウンタから鍵ストリームを作り、平文と XOR する。Poly1305 の使い捨ての鍵は、ChaCha20 の最初のブロックから暗号化のたびに作る。ChaCha20 と XChaCha20 の違いは nonce の長さだけ(12バイトと24バイト)。XChaCha20 は24バイトの先頭16バイトと鍵から HChaCha20 で副鍵を作り、残りを nonce にして ChaCha20 を回す。追加の手間は1ブロック分で、安全性は変わらない。
- **保証**: AEAD の保証すべて。
- **守るもの**: データの中身と改ざん。
- **SPOF・弱点**: nonce の再利用は致命的。KeePass の「ChaCha20」は Poly1305 なしなので AEAD ではない(改ざん検知は、暗号文のブロックごとに付ける HMAC-SHA256 が別に担っている)。
- **推奨**: 自前で nonce を管理するなら XChaCha20-Poly1305。24バイトの nonce を毎回ランダムに作っても、衝突をほぼ気にしなくてよい。ChaCha20-Poly1305(12バイト)を選ぶのは、仕様で決まっているとき。TLS 1.3、HPKE、WireGuard などは ChaCha20-Poly1305 だけを定めていて、XChaCha20 は IETF のドラフト止まりで標準になっていない。HPKE のように鍵を毎回使い捨てにするなら、nonce が短くても困らない。

### nonce / IV(Initialization Vector)

- **何か**: 暗号化ごとに変える値。秘密ではない。
- **目的**: 同じ鍵と同じ平文から、毎回違う暗号文を作る。
- **仕組み**: カウンタかランダム値。暗号文の先頭に付けて保存する。
- **保証**: 同じ内容を暗号化しても、同じだと分からない。
- **守るもの**: パターンの漏洩や、nonce 再利用による鍵の破綻から。
- **SPOF・弱点**: 再利用が最大の失敗要因。VM のスナップショットや状態の巻き戻しでカウンタが重複しやすい。
- **推奨(安全な実装パターン)**: 上から順に安全です。
  1. **暗号化のたびに鍵を新しくする**: HPKE は毎回使い捨ての鍵を作るので、nonce の重複が原理的に起きない。cw のアイテムはこれ。
  2. **XChaCha20-Poly1305 とランダムな 24バイト nonce**: 状態を持たずに済み、巻き戻しにも強い。
  3. **AES-256-GCM とランダムな 12バイト nonce**: 1つの鍵での暗号化回数を数え、上限の手前で鍵を替える。
  4. **AES-256-GCM-SIV**: nonce を誤って再利用しても、同じ平文だと分かる以上の被害が出ない(nonce 誤用耐性)。SIV は Synthetic Initialization Vector の略で、先に nonce、AAD、平文全体から MAC(タグ)を計算し、そのタグを CTR(AES-256-GCM の項で説明)暗号化の IV に使う。同じ入力なら同じ出力になるので、再利用で漏れるのは「同じ平文だった」ことだけ。その代わり平文を2回読むので、流しながらの暗号化はできず、少し遅い(RFC 8452)。
  5. **避ける**: 永続化したカウンタを nonce にする方式。バックアップからの復元で巻き戻ると、重複が起きる。

### AAD(Additional Authenticated Data、追加認証データ)

- **何か**: 暗号化はしないが、改ざん検知の対象には含めるデータ。
- **目的**: 暗号文を、その文脈(item ID、vault ID、版)に結びつける。
- **仕組み**: 暗号化と復号の両方で同じ AAD を渡す。違えばタグ検証で失敗する。
- **保証**: 暗号文が、別の項目や別の vault へすり替えられていない。
- **守るもの**: 暗号文の入れ替え攻撃から。
- **SPOF・弱点**: AAD に何を入れるかは設計者の責任。入れ忘れた属性はすり替え放題になる。
- **推奨**: 形式の版、vault ID、item ID、アイテムの版を、固定順の正規化した形(CBOR など)で入れる。

### HMAC(Hash-based Message Authentication Code)

- **何か**: ハッシュ関数と鍵から作るメッセージ認証コード(MAC)。
- **目的**: データが改ざんされていないこと、正しい鍵の持ち主が作ったことを確かめる。
- **仕組み**: 鍵とデータを、決まった手順で2回ハッシュする。HKDF や PRF 拡張の内部でも使われる部品。
- **保証**: 完全性と、鍵の保持者による作成(真正性)。
- **守るもの**: データの改ざんから。
- **SPOF・弱点**: 共通鍵なので、検証できる者は偽造もできる。第三者への証明には署名を使う。
- **推奨**: HMAC-SHA256。暗号文の改ざん検知には直接使わず AEAD に任せる。単体で使うのは、平文データの完全性確認などに限る。比較は定数時間で行う。

### 従(旧方式): AES-CBC と Encrypt-then-MAC

- **何か**: AES-CBC(Cipher Block Chaining)は、前のブロックの暗号文を次のブロックに混ぜる古典的なモード。改ざん検知がないので、HMAC を「暗号化してから暗号文に付ける」(Encrypt-then-MAC)形で組み合わせて使う。
- **目的**: AEAD が普及する前に、機密性と完全性を両立させていた方法。Dashlane と KeePass が採用している。Bitwarden は、暗号化の version 1 のアカウント(2026年11月より前に作られたもの)と組織のデータがこの方式で、それ以降に作られる version 2 のアカウントの vault は XAES-GCM。**他製品の採用方式 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)
- **仕組み**: ランダムな 16バイトの IV とパディングで暗号化し、暗号文に HMAC を付ける。復号の前に HMAC を検証する。
- **保証**: 正しく組めば AEAD と同等。
- **守るもの**: データの中身と改ざん。
- **SPOF・弱点**: CBC 単独ではパディングオラクル攻撃で解読されうる。暗号用と MAC 用の鍵の分離、検証の順序など、組み立てを自前で行うぶん実装ミスの余地がある。
- **推奨**: 新規では選ばない。AES-256-GCM か XChaCha20-Poly1305 を使う。既存データを読む互換のためだけに実装する。

## 鍵の包み方

「鍵で鍵を暗号化する」ことで、データを再暗号化せずに解錠手段だけを変えられるようになります。パスワード管理ツールの鍵階層は、すべてこの考え方の積み重ねです。

### DEK(データ暗号鍵)

- **何か**: 実際にデータを暗号化する鍵。cw のアイテムでは、HPKE が暗号化のたびに作って使い捨てる鍵がこれに当たる。cw が包んで保存するのは、その鍵を取り出すための vault 秘密鍵(X25519)。
- **目的**: データの暗号化と復号。
- **仕組み**: CSPRNG で生成する。パスワードからは導出しない。
- **保証**: パスワードの強さに関係なく、暗号そのものは 256bit の強度を持つ。
- **守るもの**: データ本体。
- **SPOF・弱点**: これを失えばデータは復元不能。平文で置かず、必ず KEK で包んで保存する。

### KEK(鍵暗号鍵)

- **何か**: DEK を暗号化(ラップ)するための鍵。
- **目的**: DEK を安全に保存し、解錠手段と結びつける。
- **仕組み**: パスワードや FIDO などの要素から導出する(例: cw のスロットの HKDF(D ‖ F))。DEK を AEAD で包む。
- **保証**: KEK を作る要素が揃わない限り、DEK を取り出せない。
- **守るもの**: DEK。
- **SPOF・弱点**: KEK を作る要素のどれかを失うと、そのスロットは開かない。

### エンベロープ暗号

- **何か**: 「DEK でデータを暗号化し、DEK を KEK で包む」二段構えの総称。KMS の標準的な使い方でもある。
- **目的**: パスワード変更や KDF の強化を、データの再暗号化なしで行う。
- **仕組み**: 解錠手段を変えたいときは、包まれた DEK を開いて新しい KEK で包み直すだけ。
- **保証**: 解錠手段の変更が、データ量にかかわらず一瞬で済む。
- **守るもの**: 運用の柔軟性と、鍵の階層ごとの隔離。
- **SPOF・弱点**: 包み直しても DEK そのものは変わらない。DEK が漏れた疑いがあるなら、DEK のローテーション(全データの再暗号化)が必要。

### keyslot(鍵スロット)

- **何か**: 同じ DEK を、異なる KEK で包んだものを複数並べておく方式。LUKS(Linux Unified Key Setup)は Linux 標準のディスク暗号化形式で、ディスクの先頭にあるヘッダに、ディスクの暗号鍵を複数のパスフレーズや鍵ファイルでそれぞれ包んだスロットを並べている。この方式をそこから借りた呼び名。
- **目的**: 複数の解錠手段(Touch ID、passkey、リカバリキーなど)を独立に持つ。
- **仕組み**: スロットごとに別の KEK で DEK を包む。どれか1つが開けば DEK が得られる。包みを2段にすることもできる。スロットは全スロット共通の解錠鍵を包み、その解錠鍵と別の要素から作る鍵で、守りたい鍵を包む。cw はこの形で、スロットが HKDF(D ‖ F) で解錠鍵 S を包み、vault ラップが HKDF(D ‖ S ‖ P) で vault 秘密鍵を包む。2段にすると、後段の要素(cw ならパスフレーズ由来の P)を変えるときに包み直すのが後段の1つで済み、各スロットの F(他人の passkey など)を集めなくてよい。
- **保証**: 1つの手段を失っても、他のスロットで開ける。スロットの追加・削除は他のスロットに影響しない。
- **守るもの**: 可用性。
- **SPOF・弱点**: 全体の強度は、最も弱いスロットで決まる。全スロットに共通する要素(cw なら D)と、スロットの後ろに1つだけ置く包みの要素(cw なら vault ラップの P)が、全体の SPOF になる。

## 公開鍵暗号と署名

公開鍵暗号は「誰でも暗号化できるが、復号できるのは秘密鍵の持ち主だけ」、署名は「誰でも検証できるが、作れるのは秘密鍵の持ち主だけ」という非対称性を提供します。新規開発では、暗号化は HPKE(X25519)、署名は ES256 を選びます。署名を ES256 にするのは、Apple の環境で使える「取り出せない鍵」とプラットフォームの passkey が、どちらも P-256 だからです。鍵共有も、Secure Enclave の鍵で行う箇所は P-256 になります。

### HPKE(Hybrid Public Key Encryption)

- **何か**: 公開鍵暗号を「KEM + KDF + AEAD」の3つの部品で組み立てる標準(RFC 9180)。この節の ECDH と、前の節の HKDF・AEAD を束ねる枠のような用語。
- **目的**: 公開鍵で任意のデータを暗号化する方法を、安全な組み合わせとして固定する。
- **仕組み**: 中の部品の対応は次の通り。
  - **KEM(鍵カプセル化)**: 使い捨ての共有鍵を作り、受信者だけが取り出せる形にする。DHKEM(X25519, HKDF-SHA256) は、X25519 の ECDH と HKDF でこれを実現する。
  - **KDF**: 共有鍵から AEAD の鍵と nonce を作る。HKDF-SHA256。
  - **AEAD**: データ本体を暗号化する。ChaCha20-Poly1305 か AES-256-GCM。
- **保証**: 受信者の秘密鍵の持ち主だけが復号できる。暗号化のたびに鍵が変わるので、nonce の再利用が起きない。
- **守るもの**: 暗号化したデータ。
- **SPOF・弱点**:
  - 受信者の公開鍵が本物であることが前提。
  - 基本モードは送信者を認証しない。公開鍵を知っていれば誰でも暗号文を作れるので、AAD が防ぐのは既存の暗号文を別の文脈へ移すことだけで、暗号文を丸ごと作り直して差し替えることは防がない。誰が書いたかは別に署名で保証する。
  - 前方秘匿性がない。受信者の秘密鍵が漏れると、その鍵で暗号化した過去の暗号文もすべて読まれる。
  - X25519 や P-256 の鍵共有は、十分な規模の量子計算機で破られる。暗号文を長く保存する用途では、今のうちに盗まれた暗号文が後から復号される対象になる。
- **推奨**: 外から見たときは「スイートを1つ選んでライブラリに渡す」だけで、中の部品を個別に選ぶ必要はない。スイートは DHKEM(X25519, HKDF-SHA256)、HKDF-SHA256、ChaCha20-Poly1305 の組み合わせ。Rust なら `hpke` クレートがある。保存する暗号文には、書き手の署名を添える。暗号文を何年も保存するなら、耐量子の KEM(ML-KEM)を X25519 と組み合わせるハイブリッドの KEM を検討の対象に入れる。**公開鍵暗号 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)

### ECDH(Elliptic Curve Diffie-Hellman) / X25519

- **何か**: 楕円曲線を使った鍵共有。X25519 は Curve25519 上の ECDH で、HPKE の KEM の中身。
- **目的**: 2者が、秘密を送り合わずに同じ共有秘密を得る。
- **仕組み**: 自分の秘密鍵と相手の公開鍵から、両者で同じ値が計算できる。
- **保証**: 通信を盗聴されても、共有秘密は分からない。
- **守るもの**: 鍵交換の秘密性。
- **SPOF・弱点**: 相手の公開鍵が本物かどうかは保証しない(中間者攻撃)。出力は生の値なので、必ず HKDF に通してから鍵として使う。
- **推奨**: 単体で使うより HPKE 経由で使う。曲線は X25519。ただし Secure Enclave の楕円曲線は P-256 だけなので、SE の鍵で ECDH する cw のデバイス要素 D と Touch ID スロットは P-256 になる。

### 電子署名(Ed25519 / ECDSA)

- **何か**: 秘密鍵で作り、公開鍵で検証する認証データ。
- **目的**: データの作成者を証明し、改ざんを検知する。第三者にも検証できる。
- **仕組み**: Ed25519 は EdDSA の一種で、曲線とハッシュが固定され、署名は決定的(同じ入力なら同じ署名)。ECDSA は曲線(P-256、P-384、secp256k1 など)とハッシュの組み合わせにバリアントがあり、署名のたびに乱数を使う。アルゴリズム名が曲線まで決めるかどうかは、形式ごとに違う。
  - **JOSE の `alg`**: ES256 は「P-256 と SHA-256 の ECDSA」で、曲線まで決まる。Ed25519 は `"Ed25519"` と書く。`"EdDSA"` は Ed25519 と Ed448 の両方を含む名前で、非推奨になった(RFC 9864)。既にある `"EdDSA"` の署名を検証するときは、鍵の `crv` まで確認する。
  - **COSE の `alg`**: ES256(-7)も EdDSA(-8)も曲線を決めず、鍵の `crv` で決まる。WebAuthn は -7 を P-256 に、-8 を Ed25519 に限定している。RFC 9864 が足した曲線まで決める番号(-9、-19)は、対応していない実装が多いので、WebAuthn は -7 と -8 を使うよう勧めている。passkey の COSE 鍵を受け取るときは `crv` を確認する。
- **保証**: 秘密鍵の持ち主が、そのデータに署名した。
- **守るもの**: 完全性と真正性。
- **SPOF・弱点**: 秘密鍵が漏れれば、誰でも偽造できる。ECDSA は乱数が偏ると秘密鍵が漏れる。署名は暗号化ではないので秘密を守らず、値が毎回変わりうるので鍵の材料にもならない。
- **推奨**: 既定は ES256。**署名 alg 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)
  - 第一の理由は、Apple の環境で使える「取り出せない鍵」が、楕円曲線では P-256 だけであること。Secure Enclave の楕円曲線の鍵は P-256 に限られ、Ed25519 の鍵は作れない。Apple のプラットフォームの認証器(iCloud キーチェーンの passkey)が作る credential も ES256(COSE の -7)だけ。署名鍵をハードウェアに閉じ込める構成と、passkey の検証と鍵の扱いを1つにまとめる構成では、ES256 しか選べない。第二の理由は、ライブラリと相手側の対応が最も広いこと。根拠にした一次資料は reference の `auth-patterns/webhook-jws-jwks` の alg の項に並べてある。
  - Ed25519 を選んでよいのは、ハードウェアの鍵を使わず、署名する側と検証する側の両方のライブラリが対応している構成。署名が決定的で、ECDSA のように署名ごとの乱数に安全性を預けない利点がある。
  - ML-DSA(耐量子の署名)は JOSE と COSE に登録済みで(RFC 9964)、macOS 26 以降の Secure Enclave も鍵を持てる。今は既定にしない。使える OS が限られ、ライブラリの対応が一部で、署名が数キロバイトになる。
  - 署名の形は場面で違う。JWS の ES256 は r と s を連結した64バイト、WebAuthn の ES256 は ASN.1 DER。両方を扱うコードで取り違えない。
  - cw では、SE 鍵の署名(アイテムと PasskeyRegistry の保護)と passkey の検証が ES256。passkey を受け付ける側は、登録時に ES256(-7)、RS256(-257)、EdDSA(-8)の3つを受け付ける(WebAuthn Level 3 が、幅広い認証器に対応する RP に勧める組)。

### 従(旧方式): ECIES(Elliptic Curve Integrated Encryption Scheme)

- **何か**: ECDH と共通鍵暗号を組み合わせた、楕円曲線版の公開鍵暗号方式。HPKE の前身にあたる。
- **目的**: 公開鍵で任意のデータを暗号化する。
- **仕組み**: 使い捨ての鍵ペアと受信者の公開鍵で ECDH し、KDF を通して AEAD でデータを暗号化する。
- **保証**: 受信者の秘密鍵の持ち主だけが復号できる。
- **守るもの**: 暗号化したデータ。
- **SPOF・弱点**: 実装ごとに細部がばらばらで、相互運用性が低い。
- **推奨**: 新規では選ばない。HPKE を使う。Apple の `SecKeyCreateEncryptedData` は ECIES なので、Security framework を使う既存コードで出会う。

### 従(旧方式): RSA-OAEP

- **何か**: RSA(Rivest-Shamir-Adleman)で暗号化するときの、安全なパディング方式(Optimal Asymmetric Encryption Padding)。
- **目的**: 公開鍵で小さなデータ(主に DEK)を暗号化する。1Password や Bitwarden の vault 鍵共有で使われている。
- **仕組み**: 平文にランダム性を混ぜてから RSA で暗号化する。
- **保証**: 秘密鍵の持ち主だけが復号できる。
- **守るもの**: 共有される DEK。
- **SPOF・弱点**: 鍵が大きく(2048bit 以上)、処理も遅い。古いパディング方式(PKCS#1 v1.5)は攻撃されやすい。
- **推奨**: 新規では選ばない。暗号化は HPKE、署名は ES256 を使う。

## 鍵の表現と信頼

公開鍵暗号の最大の弱点は「その公開鍵が本当に相手のものか」です。ここに並ぶ用語は、鍵を表現する形式と、その真正性を確かめる方法です。

### JWK / JWKS

- **何か**: 鍵を JSON で表す形式(JWK、RFC 7517)と、その集合(JWKS)。
- **目的**: 鍵を言語や実装に依存しない形でやり取り・保存する。
- **仕組み**: `kty`(鍵の種類)、`kid`(鍵 ID)、`alg` と、鍵の値を持つ。1Password の keyset もこの形式。
- **保証**: 形式の統一だけ。真正性や秘密性は何も保証しない。
- **守るもの**: なし(器にすぎない)。
- **SPOF・弱点**: 真正性は取得経路(HTTPS や署名)に依存する。秘密鍵を含む JWK は、必ず暗号化して保存する。

### thumbprint(鍵の指紋)

- **何か**: 公開鍵の必須項目を正規化してハッシュした短い値(RFC 7638)。
- **目的**: 長い公開鍵を、短い値で比べられるようにする。
- **仕組み**: 例えば SHA-256 で 32バイト。人が見比べるときは16進や絵文字などに変換する。
- **保証**: thumbprint が一致すれば、同じ鍵。
- **守るもの**: 鍵のすり替えの検知。
- **SPOF・弱点**: 最初に比べる値を、信頼できる経路で入手している必要がある。

### TOFU / ピン留め

- **何か**: 最初に見た鍵を信じて記録し、以後はそれと一致するかだけを確認する方式。SSH の `known_hosts` が代表例。
- **目的**: PKI を使わずに、鍵のすり替えを検知する。
- **仕組み**: 初回の鍵(または thumbprint)を保存し、次回以降に違う鍵が来たら警告する。
- **保証**: 初回以降のすり替えを検知できる。
- **守るもの**: 中間者攻撃(初回以外)から。
- **SPOF・弱点**: 初回接続そのものが攻撃されていれば守れない。正当な鍵の変更と攻撃を区別する手順が必要。

### Key Transparency

- **何か**: 公開鍵を、追記しかできない公開ログに登録する仕組み。Proton や WhatsApp が採用。
- **目的**: サーバが特定のユーザーにだけ偽の鍵を見せる攻撃を、後から検知可能にする。
- **仕組み**: Merkle tree で全登録を要約したルートを公開し、各クライアントや監査者が一貫性を検証する。
- **保証**: 全員に同じ鍵が見えている。過去の登録は書き換えられていない。
- **守るもの**: 鍵の配布サーバの裏切りから。
- **SPOF・弱点**: 監査する人がいなければ意味がない。検知はできても、すり替えそのものは防げない(事後に分かる)。

### SRI(Subresource Integrity)

- **何か**: Web ページが読み込むスクリプトのハッシュを、HTML に書いておく仕組み。
- **目的**: CDN などで配信されるスクリプトが、改ざんされていないことを確かめる。
- **仕組み**: `<script integrity="sha384-…">` の値と、取得したファイルのハッシュを、ブラウザが照合する。
- **保証**: 読み込まれたスクリプトが、HTML の作成者が意図したもの。
- **守るもの**: 配信経路での改ざんから。
- **SPOF・弱点**: HTML 自体を配信するオリジンを乗っ取られれば、ハッシュごと書き換えられる。

## パスワード認証プロトコル

普通のログインは、パスワード(またはそのハッシュ)をサーバに送ります。ここに並ぶ方式は、パスワードを一切送らずに「知っていること」を証明し、サーバに保存される値からもパスワードを試せないようにするためのものです。

### PAKE(Password-Authenticated Key Exchange)

- **何か**: パスワードを送らずに、相互認証と鍵共有を同時に行うプロトコルの総称。
- **目的**: パスワードを、ネットワークにもサーバにも渡さない。
- **仕組み**: パスワードを数学的に組み込んだ鍵交換を行う。両者のパスワードが一致したときだけ、同じセッション鍵になる。
- **保証**: 通信を盗聴・改ざんされても、攻撃者は1回の通信で1回しかパスワードを試せない。
- **守るもの**: 通信路上のパスワード。
- **SPOF・弱点**: サーバに保存される検証値の扱いは方式によって違う(SRP と OPAQUE の差)。

### SRP(Secure Remote Password)

- **何か**: 古くからある PAKE の一つ。1Password、Proton、Apple の iCloud キーチェーンのエスクローで使われている。
- **目的**: パスワードを送らずにログインする。
- **仕組み**: 登録時に、パスワードから計算した verifier をサーバに保存する。ログイン時は、それを使った鍵交換で照合する。
- **保証**: 通信路からパスワードは漏れない。
- **守るもの**: 通信中のパスワード。
- **SPOF・弱点**: verifier が漏れると、オフライン総当たりができる(これはサーバが1台のどの方式でも同じ)。SRP に固有なのは、salt が認証の前に平文でクライアントへ渡ることで、攻撃者は salt を先に手に入れて候補のパスワードを事前に計算しておけるので、verifier が漏れた時点ですぐに破られる。1Password は、Secret Key を混ぜること(2SKD)で、verifier が漏れても総当たりが成り立たないようにしている。

### OPAQUE

- **何か**: SRP の弱点を改良した新しい PAKE(RFC 9807)。
- **目的**: verifier が漏れたときの被害も抑える。
- **仕組み**: salt に相当する処理を OPRF(紛失通信型の擬似乱数関数)で行うので、サーバ側の秘密がないとパスワードを試せない。
- **保証**: 事前計算ができない。攻撃者は、サーバの値が漏れた後で初めて総当たりを始められる。
- **守るもの**: 通信中のパスワードと、サーバに保存された値。
- **SPOF・弱点**: 実装例がまだ少ない。サーバの OPRF 鍵とデータベースが両方漏れれば、総当たりは可能になる(サーバが1台の方式では避けられない)。

### 2SKD(Two-Secret Key Derivation)

- **何か**: 1Password の方式。パスワードと、端末にある高エントロピーの Secret Key の2つから鍵を導出する。
- **目的**: サーバのデータが漏れても、オフライン総当たりを成立させない。
- **仕組み**: PBKDF2(パスワード)と HKDF(Secret Key)の結果を XOR して、暗号鍵(AUK)と SRP 用の値をそれぞれ作る。
- **保証**: Secret Key を持たない攻撃者は、パスワードが弱くても解読できない。
- **守るもの**: サーバに保存された暗号文と verifier。
- **SPOF・弱点**: Secret Key を失うと、本人も復元できない。cw の D は、この Secret Key を SE が保管する版と考えられる。

## ハードウェアによる保護

ソフトウェアだけで鍵を守ると、「鍵を使えるプロセス」と「鍵を盗めるプロセス」が同じになってしまいます。ハードウェアの保護は、鍵を外に出さずに使わせることで、この2つを分けます。

### Secure Enclave(SE)

- **何か**: Apple の SoC に内蔵された、独立したセキュリティ用プロセッサ。
- **目的**: 秘密鍵を、OS からも取り出せない場所に置いて使う。
- **仕組み**: 鍵を SE 内で生成し、署名や鍵共有だけを SE が行う。楕円曲線は P-256 だけ(ECDSA と ECDH)。macOS 26 / iOS 26 以降は、CryptoKit から ML-KEM(768、1024)と ML-DSA(65、87)の鍵も SE に作れる。外に出るのは、その SE でしか使えない暗号化済みの blob だけ。アクセス制御(Touch ID など)も SE が強制する。**SE の鍵種 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)
- **保証**: 鍵はその Mac の外では使えない。ディスクを丸ごと盗まれても鍵は複製できない。
- **守るもの**: 秘密鍵の抽出から。
- **SPOF・弱点**:
  - その Mac(ロジックボード)が壊れれば鍵も失われる。
  - 鍵を「使う」ことは防げない。blob はその Mac の SE には縛られるが、アプリには縛られない。認証不要の SE 鍵は、blob を読めるプロセスなら誰でも使える。blob を作ったプログラムである必要も、entitlement も要らない(観測: ad-hoc 署名で identifier の違うプログラムが、別のプログラムの作った blob を読み込み、ECDH で同じ共有値を得た)。
  - だから、blob を他のプロセスに読ませないことが守りの柱になる。cw は、blob を cw の access group を付けた data protection keychain の項目に置く。

### TPM(Trusted Platform Module)

- **何か**: PC 向けの、SE と同じ役割を持つセキュリティチップ(またはファームウェア)。
- **目的**: Windows や Linux で、鍵をハードウェアに閉じ込める。
- **仕組み**: 鍵を TPM 内で生成・使用する。起動状態の測定値(PCR)に鍵を結びつけることもできる。
- **保証**: SE と同様に、鍵を外に持ち出せない。
- **守るもの**: 秘密鍵の抽出から。
- **SPOF・弱点**: SE と同じく「使うこと」は防げない。Palo Alto Networks の Unit 42 が公表した Pass-ta-key(Windows 上の Chrome で、Google に同期した passkey が対象)は、まさに TPM の鍵を取り出さずに勝手に署名させる攻撃だった(報道に基づく記述)。

### HSM(Hardware Security Module)

- **何か**: サーバ用の、耐タンパー性を持つ鍵管理装置。
- **目的**: 組織やクラウドの鍵を、運用者からも守る。
- **仕組み**: 鍵は HSM 内にしかなく、ファームウェアに書かれたポリシー(試行回数制限など)を強制する。Apple の iCloud キーチェーンのエスクローは、HSM クラスタで10回の試行制限をかけている。
- **保証**: ポリシーが、管理者を含めて誰にも迂回できない(と主張される)。
- **守るもの**: 短い PIN を、総当たりから守る。
- **SPOF・弱点**: ファームウェアと運用(管理カードの破棄など)を信頼するしかなく、外部からは検証できない。

### TEE / Confidential Computing

- **何か**: CPU 内に隔離された実行環境(AWS Nitro Enclaves、Intel SGX、AMD SEV など)。
- **目的**: サーバ上の処理を、クラウドの運用者からも見えなくする。Dashlane の SSO が使用。
- **仕組み**: 隔離環境で動くコードのハッシュをアテステーション(遠隔証明)し、クライアントはそれを確認してから秘密を渡す。
- **保証**: 秘密を受け取るのが、検証済みの特定のコードだけ。
- **守るもの**: 処理中のデータを、サーバの運用者から。
- **SPOF・弱点**: CPU メーカーとクラウド事業者のハードウェアを信頼する必要がある。サイドチャネル攻撃の歴史もある。

### キーチェーン(data protection keychain / ファイル型キーチェーン)

- **何か**: macOS の秘密保存の仕組み。新しい data protection keychain と、旧来のファイル型キーチェーンの2系統がある。
- **目的**: アプリごとに、パスワードや鍵を安全に保存する。
- **仕組み**: data protection 型は、entitlement に基づく access group で読めるアプリを決める。ファイル型は、コード署名に基づく ACL(信頼するアプリの一覧)で決める。
- **保証**: 許可したアプリだけが、確認なしで読める。誰を許可したことになるかは、項目の作り方で決まる(下の弱点)。
- **守るもの**: 他のアプリからの読み出しから。
- **SPOF・弱点**:
  - data protection 型は、CLI では provisioning profile が必要になり扱いにくい。
  - ファイル型は、作り方によっては誰も絞れない。`security` コマンドで作った項目や「全アプリ可」の項目は、同じユーザーのどのプロセスも確認なしで読める。信頼するアプリを自分のバイナリだけにして作った項目で、初めて読み手が絞られる(作り方と確かめ方は reference の `macos-process-protection` の、保存する秘密の置き場の項目。無人で読むツールの置き方は reference の `keychain-secrets`)。
  - ファイル型で許可ダイアログが出るのは、読み手の designated requirement が ACL と合わないとき。ad-hoc 署名は requirement がビルドごとに変わるので、ビルドのたびに出る。Developer ID で署名していれば、更新しても requirement は変わらず、ダイアログは出ない。
  - どちらも「同じアプリになりすませる者」は防げない。

### アクセス制御(SecAccessControl)

- **何か**: SE 鍵やキーチェーン項目に付ける、「使うときに何を要求するか」の設定。
- **目的**: 鍵を使う瞬間に、本人の存在を確認させる。
- **仕組み**: `biometryAny`(登録済みのどの指紋でも可)、`biometryCurrentSet`(指紋の登録が変わると無効になる)、`devicePasscode`(ログインパスワード)などを組み合わせる。
- **保証**: 要求が満たされない限り、SE が鍵の使用を拒否する。
- **守るもの**: 端末を乗っ取ったマルウェアによる、鍵の無断使用から。
- **SPOF・弱点**: Touch ID のセンサーが壊れると、biometry だけを要求する鍵は使えなくなる。`biometryCurrentSet` は指紋を登録し直すだけで無効になる。

## FIDO

FIDO は、パスワードの代わりに公開鍵の署名でログインする仕組みです。署名は本人確認には使えますが、鍵の材料にはなりません。暗号化に使えるのは PRF 拡張だけです。

### WebAuthn

- **何か**: ブラウザから FIDO 認証器を使うための W3C 標準 API(`navigator.credentials.create()` / `get()`)。
- **目的**: Web サイトが、フィッシングに強い公開鍵認証を使えるようにする。
- **仕組み**: 登録時に認証器が鍵ペアを作り、公開鍵をサイトに渡す。認証時はサイトの challenge に認証器が署名し、サイトが公開鍵で検証する。
- **保証**: その秘密鍵を持つ認証器で、本人(Touch ID などで確認済み)が承認した。
- **守るもの**: 認証を、フィッシングとリプレイから守る。
- **SPOF・弱点**: 署名なので秘密は守らない。登録済みの公開鍵の一覧が改ざんされると、攻撃者の鍵を通してしまう(cw の PasskeyRegistry に完全性保護が必要な理由)。

### passkey

- **何か**: パスワードなしで使う FIDO 認証情報の通称。端末をまたいで同期するもの(synced passkey)と、1つの端末やセキュリティキーに束縛されたもの(device-bound passkey)の両方を指す。
- **目的**: パスワードの代わりに使える FIDO 認証。同期するものは、端末をまたいで使え、紛失にも強い。
- **仕組み**: 同期するものは、秘密鍵を iCloud キーチェーンや Google パスワードマネージャーなどが E2E 暗号化して同期する。束縛されたものは、秘密鍵が作られた端末から出ない。どちらであるかは、認証器が返す backup eligible のフラグで分かる。
- **保証**: WebAuthn と同じ。同期するものは加えて、同じアカウントの別の端末でも使える。
- **守るもの**: 認証の可用性。
- **SPOF・弱点**: 同期するものは、同期元のアカウント(Apple ID や Google アカウント)が乗っ取られると passkey も渡り、可用性は同期サービスに依存する。束縛されたものは、その端末を失うと使えなくなる。

### rpId(Relying Party ID)

- **何か**: passkey を紐づけるドメイン名。例: `example.com`。
- **目的**: 別のサイトで passkey を使わせない(フィッシング対策の根幹)。
- **仕組み**: ブラウザは、ページのオリジンが rpId(またはそのサブドメイン)のときだけ、その passkey を使わせる。
- **保証**: 署名は、そのドメインのページでしか作られない。
- **守るもの**: 偽サイトでの passkey 使用から。
- **SPOF・弱点**: ドメインや配信元を失うと、その rpId の passkey はすべて使えなくなる。cw では復号に D と P も必要なので、失うのは可用性だけ。

### PRF 拡張 / hmac-secret

- **何か**: 認証器に、credential ごとの秘密で HMAC を計算させる WebAuthn の拡張。CTAP では hmac-secret と呼ぶ。
- **目的**: passkey から、暗号鍵の材料になる決定的な値を得る。
- **仕組み**: RP が salt を渡すと、認証器が「credential 固有の秘密 × salt」で HMAC を計算し、32バイトを返す。同じ credential と salt なら、毎回同じ値になる。ブラウザは、RP の渡した値をそのままではなく、固定の文字列と一緒にハッシュしてから認証器に渡す。登録(`create()`)のときに値を返さない認証器があるので、登録で値が返らなければ、続けて認証(`get()`)を1回行って値を得る。
- **保証**: その passkey で本人が承認しない限り、値は得られない。
- **守るもの**: KEK の材料(cw の F)。
- **SPOF・弱点**: 認証器、OS、ブラウザのすべてが対応している必要がある(macOS 15 / iOS 18 以降の iCloud キーチェーンなど)。値はブラウザの JS に渡るので、ページの JS を信頼する必要がある。**PRF の対応環境 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)

### ハイブリッド(クロスデバイス認証)

- **何か**: PC の画面の QR コードをスマホで読み、スマホの passkey で PC 上のログインを行う方式(旧称 caBLE)。
- **目的**: passkey がない端末から、近くのスマホの passkey を使う。
- **仕組み**: QR コードで鍵を交換し、Bluetooth で近接を確認してから、中継サーバ経由で暗号化通信する。
- **保証**: スマホが物理的に近くにある。
- **守るもの**: 遠隔からのなりすましから(近接確認により)。
- **SPOF・弱点**: Bluetooth が必要。PRF の対応が不安定で、経路によって値が変わる不具合が報告されている(iOS 18.0〜18.3 は、この経路の PRF が端末上で直接得る値と違った。iOS 18.4 / macOS 15.4 で直ったが、その後の版でも同じ症状の報告がある)。cw のリモート認可は、スマホのブラウザで直接 `get()` するので、この経路を使わない。**ハイブリッド経由の PRF の扱い 選定判断基準日: 2026-11-27**(選定を変えたらこの日付と根拠も一緒に更新する)

## 実装上の概念

暗号の部品が正しくても、メモリの扱いや書き込みの順序を間違えると秘密は漏れ、トークンは失われます。ここに並ぶのは、暗号そのものではなく、それを安全に動かすための実装パターンです。

### SecretBytes / zeroize

- **何か**: 秘密を保持するメモリ領域を、使い終わったら確実にゼロで上書きする型やライブラリ(Rust の `zeroize`、`secrecy` クレートなど)。
- **目的**: 平文の秘密がメモリに残る時間を最小にする。
- **仕組み**: Drop 時に、コンパイラの最適化で消されない方法で上書きする。`Debug` 出力を伏せ字にし、うっかりログに出さないようにする。`mlock` でスワップへの書き出しを防ぐことも多い。
- **保証**: 解放後のメモリダンプやスワップから、秘密を拾われにくくなる。
- **守るもの**: メモリ上の平文。
- **SPOF・弱点**: 使用中の秘密は守れない。コピー(`clone`、文字列化、外部ライブラリへの受け渡し)をされると、そのコピーまでは消せない。

### single-flight

- **何か**: 同じキーへの同時リクエストを1本にまとめ、全員がその結果を共有するパターン。
- **目的**: 同じ refresh や upstream への取得が、同時に何本も走らないようにする。
- **仕組み**: キーごとに「実行中の処理」を1つだけ持ち、後から来たリクエストはその完了を待つ。
- **保証**: 1つのキーについて、upstream への要求は同時に1つだけ。
- **守るもの**: refresh token の二重使用や、op の重い処理の多重起動から。
- **SPOF・弱点**: 実行中の処理がハングすると、待っている全員が止まる。タイムアウトが必須。

### refresh token ローテーション

- **何か**: refresh のたびに新しい refresh token を発行し、古いものを無効にする OAuth の運用。
- **目的**: 盗まれた refresh token の寿命を短くする。
- **仕組み**: 古いトークンの再利用を検知すると、そのトークン系列(token family)全体を失効させるサーバもある(OAuth 2.0 Security BCP、RFC 9700)。
- **保証**: 盗まれたトークンが使われれば、正規の利用者も攻撃者も締め出され、事件として表面化する。
- **守るもの**: 長期間有効な認可から。
- **SPOF・弱点**: 新しいトークンを受け取ったのに保存し損ねると、手元の古いトークンは無効で、復旧には再同意が必要になる。

### 原子的書き込み(write → fsync → rename)

- **何か**: ファイルを、「古い内容か新しい内容のどちらか」の状態にしかならないように更新する手順。
- **目的**: 書き込み中にクラッシュしても、データが壊れたり半端になったりしないようにする。
- **仕組み**: 一時ファイルに書いて fsync で確実にディスクに載せ、rename で置き換える。必要ならディレクトリも fsync する。
- **保証**: クラッシュの後でも、どちらかの完全な版が残る。
- **守るもの**: 新しい refresh token や、スロットファイルの整合性。
- **SPOF・弱点**: macOS では `fsync` がディスクのキャッシュまでは保証しないので、確実にするなら `F_FULLFSYNC` を使う。

## cache-warden での使いどころ

cw の設計は、ここまでの用語のほぼすべてを組み合わせたものです。全スロットに共通する D(ホスト)と、vault ラップに混ぜる P(時間)が、設計上意図した SPOF です。

| cw の部品 | 使う用語 | 役割 |
| --- | --- | --- |
| デバイス要素 D | Secure Enclave、ECDH、HKDF | 認証なしの SE 鍵で ECDH し、ホストにしか計算できない値を作る |
| パスフレーズ要素 P | Argon2id、AEAD、AAD | Argon2id の結果を D で暗号化して保存し、発行時刻と寿命を AAD で保護する |
| Touch ID スロットの F | Secure Enclave、アクセス制御、ECDH | biometry 付きの SE 鍵で ECDH する |
| passkey スロットの F | WebAuthn、PRF 拡張、rpId | 複数の rpId に登録した passkey の PRF 出力 |
| リカバリキースロットの F | CSPRNG | 印刷して保管するランダム値 |
| 各スロットの KEK | HKDF、keyslot | HKDF(D ‖ F)、info にスロット種別を入れる。全スロット共通の解錠鍵 S を包む |
| vault ラップ | HKDF、AEAD、AAD、keyslot | HKDF(D ‖ S ‖ P) で vault 秘密鍵を包む。パスフレーズを変えたときに包み直すのはここだけ |
| vault 鍵 | X25519、HPKE | 公開鍵で書き込み、秘密鍵で読み出す |
| 各アイテム | HPKE、AEAD、AAD、電子署名 | item ID と版を AAD に入れて、既存の暗号文を別のアイテムへ移すことを防ぐ。丸ごとの差し替えは、書き手の署名で防ぐ |
| PasskeyRegistry | 電子署名、TOFU / ピン留め | SE の署名鍵 `K_sig` で完全性を守り、ロールも記録する |
| メモリ上の値 | SecretBytes / zeroize | ttl ごとに破棄する |
| OAuth の refresh | single-flight、refresh token ローテーション、原子的書き込み | 新しいトークンを永続化してから返す |
| リモート認可ページ | SRI、rpId | 別のオリジンから読み込むスクリプトの改ざんを検知する。ページを配るオリジンそのものの乗っ取りは検知できない |

### アイテムの真正性と巻き戻し

- **書き手の署名**: HPKE の基本モードは書き手を認証せず、vault 公開鍵はファイルに平文で置く。ファイルを書ける相手は、任意の値を暗号化してアイテムを丸ごと差し替えられる。cw はアイテムに書き手の署名を付けてこれを防ぐ。署名鍵は SE の署名鍵 `K_sig` で、SE から取り出せず、ES256 の署名にだけ使う。
- **巻き戻しの錨**: 署名は、正しく署名された古いファイルへの巻き戻しを防がない。単調に増える版や epoch を、マルウェアが書き換えられない場所(cw の access group を付けたキーチェーンの項目)に置き、ファイルの版と照合する。この置き場が外から消せない・巻き戻せないことは、実機でまだ確かめていない(未確認)。

### 信頼の根を変える操作

passkey の登録やリカバリなど、信頼の根を変える操作は、ホストのローカルの Touch ID に限る。リモートの認可では行わない。登録の起点をホストに閉じる考え方は、reference の `auth-patterns/passkey-registration-local-first` と同じ。
