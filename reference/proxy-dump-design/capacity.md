# 設定、容量と並列度、クリーンアップ、保存先の権限

## 設定キー

値は**例**で、既定値はプロダクトごとに決める (どうせ適用先で設定する)。サイズの設定値は単に数字でよい。

| キー | 例 | 種別 | 説明 |
|---|---|---|---|
| `dump_max_concurrency` | `16` | ハード | 同時に active にできる dump の上限 |
| `dump_max_timeout` | `24h` | ハード | start の `timeout` に許す上限。**`dump_cleanup_ttl` 以下**にする |
| `dump_default_timeout` | `5m` | リクエストの既定 | start で `timeout` を省略した場合の値 |
| `dump_default_max_bytes` | `5MiB` | リクエストの既定 | start で `max_bytes` を省略した場合の値 |
| `dump_max_total_bytes` | `2GiB` | ハード | active な全 dump の実使用量合計の上限 (予約合計の上限ではない) |
| `dump_fs_min_free` | `1GiB` | ハード | 保存先ファイルシステムに必ず残す空き容量 |
| `dump_cleanup_ttl` | `48h` | ハード | dump ディレクトリを自動削除するまでの時間 |

`timeout` の上限を `dump_cleanup_ttl` 以下に縛るのは、削除時刻が `delete_after = start + ttl` で決まるため。上限が無いと稼働中の dump がクリーンアップに消される。

## 予約はオーバーブッキングを許す申告値

start で指定する `max_bytes` はその dump 自身の上限であり、全体の容量を確保する予約ではない。実際には使い切らない dump が多いため、active な dump の `max_bytes` 合計 (requested) が全体上限を超えても start は受け付ける。

## 実使用量ベースで判定する

全体の容量チェックは、body をディスクに書き込む時点で実使用量に対して行う。書き込みは以下をすべて満たす場合にのみ許可される。

- その dump の書き込み済みバイト数 + 書き込みサイズ ≤ その dump の `max_bytes`
- active な全 dump の実使用量合計 + 書き込みサイズ ≤ `dump_max_total_bytes`
- fs 空き容量 − 書き込みサイズ ≥ `dump_fs_min_free`

数えるのは**常にディスクに書くバイト数**で、判定は書く直前の位置に置く。圧縮を展開して保存する `store: "decoded"` ([files](files.md)) では展開後の write の位置で判定するので、decompression bomb は展開が進んだ時点で上限に当たって止まる (`decoded` 専用の上限は持たない)。index.jsonl とメタ json は数えない (上限で打ち切った後にも `truncated` と `stop` の行を書く必要がある)。

fs 空き容量は毎回計測せず、適当な間隔で cache した値を使う。

## 削除待ちの dump は考慮しない

終了済みで削除待ちの dump は `dump_max_total_bytes` の計算に含めない。ホストの空き容量は `dump_fs_min_free` で保証しており、削除待ちの dump が使う容量は fs 空き容量に自然に反映されるので、`dump_fs_min_free` の判定で間接的に効く。クリーンアップで容量が回復することは前提にしないしさせない。

## 判定のタイミング

容量による停止は、書き込みが発生した時点でのみ判定する。条件に一致する request が来ない dump は、途中で全体の容量が上限に達しても影響を受けず、`timeout` まで active のまま残る。その後 request が来た時点で空きがあれば書き込める。

全体上限に達したとき、active な dump が一斉に止まるとは限らない。上限に達した状態で書き込もうとした dump だけが止まる。

時限は timer の発火だけに頼らず、書く時点でも期限と壁時計を比べて守る (スリープで単調時計が止まり timer が遅れても、期限を過ぎた 1 本は書かない)。

## ストリームの途中で止まった場合

SSE などのストリーム型 response では、書き込みの途中で上限に達し得る。容量はチャンク単位でチェックし、途中で上限に達した場合は収まる分まで書き、その response (試行) を `truncated: true` として記録したうえで dump を停止する。request は書く前に大きさが分かるなら、書くと上限を超える時は書かずに止まる。

上限に**達した時点**で止まる (超えるのを待たない)。

## 並行書き込み時の判定

複数の dump が並行して書き込む場合の全体使用量は atomic counter で管理する。先に加算してから判定し、上限を超えていたら減算して停止する。

## 中継の速度を落とさない

動いている dump が無い間は 1 バイトも控えない。「誰も求めていなければ何もしない」を atomic の load 1 つで判定する。response は終端まで溜めて 1 件にせず、通り過ぎるチャンクをそのまま書く (溜めると上限いっぱいの本文が並列の数だけメモリに乗る)。

## クリーンアップ

`dump/{dump_id}/` は `dump_cleanup_ttl` の経過後にクリーンアップ処理で**ディレクトリごと**削除する。起点は dump の開始時刻とし、start の応答の `delete_after` で示す。中のファイルを個別には消さない (index.jsonl だけ残って本文が無い、のような半端を出さない)。

`persist: false` の dump ([api](api.md)) は保持せず、停止時にディレクトリごと削除する。

## 保存先の権限と秘密

- ディレクトリは 700、ファイルは 600 を**umask に依らず**明示的に付ける。会話や業務データの本文が入る
- 認証系ヘッダ (Authorization 等。プロダクトが「控えに持ち回さない」と決めている述語に当たるもの) はメタ json にも書かない。述語はプロダクトに 1 つだけ持ち、ダンプ用の 2 つ目の一覧を作らない
- labels は index に平文で残る。秘密を入れない ([api](api.md))
- ダンプしたファイルは本文そのもの。リポや公開物に貼らない。置き場の外へコピーした先は取得者の責任
