# タスクオーケストレーション (Phase 0-4)

「次に何をやるか」を惰性でなく判断で選ぶための実行順序の型。行動制約 (禁則) は常時ロードの rules が担う。

## 三原則

1. 完了条件を先に固定する。検証方法が書けないタスクは、まだ理解できていない
2. 主張ではなく観測を信じる。「動くはず」は証拠ではない
3. 次の一手は「いま一番リスクが高い場所」で選ぶ。元の計画の次の行ではなく

## 適用ゲート

軽微編集 (work-principles の「メインが直接行ってよい作業」)、議論レーンの調査 / PoC、手順が確定済みの runbook 実行は Phase を踏まず直接やる。迷ったら適用する。

## Phase 0: アンカー 3 行

TODO 作成の前に書く:

```
完了条件: <観測可能な形で。「〜が動く」でなく「コマンド X が出力 Y を返す」>
検証方法: <コマンド / diff / 実行結果。何を見れば完了と判定できるか>
やらないこと: <今回スコープ外にする隣接事項>
```

検証方法の行が書けない = 理解不足。書けるようになるまで先に調査する。スコープが膨らみかけたらこの 3 行と照合する。3 行はユーザへの最初の応答 or TODO 先頭に置く。

## Phase 1: 偵察と 3 値仕分け

計画の前に実物を軽く読み、読んだ情報を 3 値でラベリングする:

- 事実: 自分が観測した (コマンド出力 / ファイル内容 / 実行結果)
- 仮定: 誰かの主張・推測 (ユーザの見立て、コードコメント、issue 本文、過去ログ、自分の記憶)
- 不明: どちらでもない。埋める必要があるかをリスク順で判断

一番危険なのは事実のふりをした仮定。「〜が怪しい」という誘導は仮定としてマークして検証対象にするだけで、探索範囲をそれに限定しない。

## Phase 2: リスク順分解

独立して検証できる単位で切り、リスク順に並べる。最初にやるのは「外れたら計画全体が崩れる仮定の検証」。簡単なところから片付けて勢いをつけるのは罠 (核心が不成立なら簡単な部分の成果ごと捨てる)。各単位に検証方法を付けてから着手する。サブエージェント委譲の判断はここで行う (選定は reference の `delegation/model-effort-matrix`)。

## Phase 3: 実行ループ

1 ピースずつ進め、その場で検証する。各ピース完了ごとに次の一手を選び直す:

1. 観測は計画と矛盾していないか。矛盾したら計画側を疑う
2. いま最大のリスクはどこか。Phase 2 の順序は暫定
3. 次の行動は可逆か。不可逆操作は根拠の密度を一段上げる
4. 人間にしか答えられないことで詰まっていないか。詰まっているなら即問う

行動 vs 追加調査は手戻りコストと確認コストの比較で決める: 確認が 1 コマンドで済むなら確認、手戻りが軽微 (可逆 + 局所) なら行動。

## Phase 4: 全体検証と報告

1. 別の層で確認する。コードなら実行、文章なら初見読者として読む、設定なら再現環境で適用。作った層と同じ層の再読は検証ではない
2. 壊しに行く。空入力・境界値を実際に当てる
3. 報告に書く各原因に「症状へ寄与した証拠」を 1 つずつ持つ。なければ「寄与は未確認」と明記する
4. Phase 0 の 3 行と最終成果を照合する。「やらないこと」に入れた事項の扱いも報告に含める
5. diff を通読し、意図しない変更の混入がないか見る
