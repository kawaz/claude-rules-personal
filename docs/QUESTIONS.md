## 裁定待ち

### 👺CB-Q1: 確認待ち (C) の項目記法をチェックボックス + ラベルにするか

C は 1 機能の確認でも項目数が多くなりがちで、現行の素の箇条書きだと回答しづらい
(kawaz 実運用の所見)。

- a (推奨): `- [ ] C1a: <確認項目>` — チェックボックス + **C 付きラベル**
- b: `- [ ] a: <確認項目>` — チェックボックス + Q と同じ `a:` ラベル
- c: `- [ ] <確認項目>` — チェックボックスのみ (コメント時は行を引用して返す)

a 推奨の理由: b の `a:` は Q の `a:` と意味が違う (Q = 択一の選択肢、C = 全部
確認する項目の識別子)。同じ表記だと「C1a と答えたら a だけ OK なのか、a に指摘が
あるのか」が曖昧になる。ラベルに `C` を入れれば混同しない。

回答規約 (a 採用時): チェック = OK、指摘は `C1b: <内容>` の形で返す。

#### 背景説明 (基本省略、詳細を求められたら補充)

チェックボックスと ラベルは直交する軸なので併用しても壊れない
(チェック = 進捗の視覚化 + UI 操作で返せる / ラベル = コメントでの参照経路)。

ccmsg の markdown プレビューにチェックボックス操作を実装する案が出ているが、
それは kawaz 製ツールへの機能追加なので `dogfooding-feedback-upstream` に従い
ccmsg 側へ起票する。本 Q は先に決めるべき記法だけを扱う (記法が決まらないと
何をチェックボックスにするかが定まらないため)。

### 👺BD-Q1: 常時ロード rules の予算値をいくつにするか

[always-loaded-rules-diet](./issue/2026-07-03-always-loaded-rules-diet.md) の
受け入れ条件 4 件のうち 3 件は達成済みで、残るは「予算チェックを lint-rules に
組み込む」のみ。実装には閾値が要るが未確定 (issue 本文の「例 15k token」は
起票時の案)。

現況の実測: このリポ分 73KB (for-all 64.4KB + for-me 8.6KB)、
全 overlay 込みの実ロード **88.9KB** (概算 30k token 程度)。起票時は 127KB。

検査できるのは自リポ分 (73KB) のみ。lint は他 overlay の中身を見られないため。

- a (推奨): 現況を基準に **80KB で warning**。増加を検知しつつ、今すぐ削る
  作業は発生しない
- b: 目標値として **40KB で warning**。現況が既に超えているので、恒常的に
  warning が出続ける (= 削減の圧を掛け続ける)
- c: 予算チェックを入れない。issue の当該条件を「見送り」で close する

a 推奨の理由: b は「常に warning が出ている状態」を作り、警告の意味が薄れる
(= 見なくなる)。まず増加を止め、削減はその都度の判断で進める方が機能する。

#### 背景説明 (基本省略、詳細を求められたら補充)

lint-rules には既に「1 ファイル 5KB 超で warning」があるが、合計値の検査は無い。
本 Q は合計側の閾値を決めるもの。

実ロードは全 overlay 込みで 88.9KB だが、自リポ分は 73KB。差の 16KB は
emeradaco / syun / zunsystem の rules で、lint からは見えない。よって閾値は
自リポ分に対して設定する (= 他 overlay が太っても検知できないのは本検査の限界)。
