# pre-clear skill の改善 4 点 (llm-gateway セッション実運用フィードバック)

## 概要

`rules-personal:pre-clear` skill (state 保存フォーマット・運用) について、
llm-gateway プロジェクトでの実運用中に見つかった改善点 4 点。kawaz 合意済み。

## 背景

pre-clear は `/clear` 前にセッション状態を `XDG_CACHE_HOME` 配下へ保存し、
後継セッションがゼロコンテキストから読める自己完結ブートストラップを
提供する skill。以下 4 点は実運用で顕在化した不備。

### (1) ロード側の鮮度チェック明文化

`loaded_by` が空 (= 誰もロードしていない) でも、state ファイルの日付と
§2 の head hash を実機 (現在の main / HEAD) と照合すべき。main が進んでいたら
state 内の継続作業指示は失効扱いとし、そのまま実行せず「候補提示」に降格する。

実例: 8/15 付の state ファイルが `v0.21.1` 時点の継続作業指示を残したまま、
`v0.26.0` まで進んだセッションにロードされた (指示が古い前提のまま実行され
かねない状態だった)。

### (2) §6 を Worker & Peer Topology に拡張

現状の §6 はクロスセッション連携の引き継ぎ情報が room 番号 / `aN` のような
セッションローカルな識別子に依存している。後継セッションは元の room に
参加していないため、これらの識別子は引き継ぎ後に使えない。

代わりに **「相手の sid + cwd + 交わした約束の列挙」** だけを引き継ぐ形に
拡張する。後継は再接続時、相手に「{cwd} の新セッションです、前任の約束を
引き継ぎます」と名乗る規約とする。相手側も同じ規約に従っていれば、cwd を
キーに前任セッションとの対応関係を照合できる。

### (3) リポ外生成物の一覧欄追加

作業中にリポ外へ意図的に置いた生成物 (例: 業務 cwd を含むレポートを
`~/.cache` 配下へ退避したもの) を state に一覧として記録する欄が無い。
理由付きで一覧化し、後継が「消してよいか / 参照すべきか」を自分で判断
できるようにする。

### (4) 継続作業指示の粒度規約

継続作業指示の項目粒度が不揃いで、後継が手探りでやり直す原因になっている。
`orchestrate` skill Phase 0 の「検証方法が書ける粒度」に倣い、**1 項目 = 1
検証可能単位** を規約化する。複雑な手順は、具体的な実行コマンド例と
結果の見方 (= 何を見て成功/失敗を判断するか) まで書く。

## 受け入れ条件

- [ ] (1) state ロード時の鮮度チェック手順が pre-clear (またはロード側、
      おそらく別 skill/hook) の本文に明記されている
- [ ] (2) §6 が Worker & Peer Topology として sid + cwd + 約束列挙の形式に
      改訂されている
- [ ] (3) state フォーマットにリポ外生成物一覧欄が追加されている
- [ ] (4) 継続作業指示セクションに「1 項目 = 1 検証可能単位」の粒度規約と
      複雑手順の記述例が追加されている
