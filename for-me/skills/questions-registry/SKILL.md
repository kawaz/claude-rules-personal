# 裁定・確認待ちは docs/QUESTIONS.md に常時集約

プロジェクト内の `docs/QUESTIONS.md` に、ユーザの判断が要る項目を集約する。

**AskUserQuestion は使用禁止** (タイムアウト無しで無限待ち、リモート応答不可、
ユーザ入力中の割り込みが不快)。判断が要る時はチャット本文で尋ね (自由文回答歓迎)、
裁定を待つ間に他の作業へ進められるなら本ファイルに 👺ラベル付きで起票して参照する。

本 skill が常時ロード rule でなく統括 role の skill なのは、ユーザと直接
コミュニケーションを取るのがメインコンテキストだけだから (= ワーカーは
AskUserQuestion も QUESTIONS.md への起票も行わない)。

## Why

- ユーザが「何待ちか」をチャット履歴から掘り返す手間の削減
- AI にリストと説明を再生成させるコストの削減 (今何待ち? を撲滅)
- 実装完了や質問提起が散発的に発生してTLに流れてしまい、未確認のまま亡失される問題を、本ファイルが解決する
- セッション境界・並行セッションを越えて裁定・確認キューが共有される

## テンプレート (運用規約の本体)

ファイルが空ならこれをテンプレとして運用する。

```docs/QUESTIONS.md
# 裁定・確認待ち一覧 (ユーザ用)

## 運用規約

<details>
<summary>ゼロコンテキストエージェント向け（本セクションは消さない）</summary>

- 裁定/確認待ち項目を 1項目=1ラベル=1セクション で記載
- ラベル形式: XX-Q1（バッチやセッション内で一意な短プレフィクス、Qn単独の使い回し禁止、長期一意性は不要)
- 依頼形式: 「👺XX-Q1 の裁定お願いします」（参照用途ではラベルに👺を付けない。誤陽性がユーザのハイライト/アラームを汚す）
- チャット提示と同一ターンで本ファイルに記録 + path 指定 commit (push はリリース窓に同乗)
- 裁定が下りたら該当セクションを即削除し、内容は正規の記録先 (DR / issue / journal / close_reason) へ反映。本ファイルは常に「現在待ち」だけを持つ
- 参照は[]()で提示（リポ内は相対、リポ外はフルパス）
- 初版質問/依頼は長文で書かない（ユーザが説明を求めらたら本ファイルに説明を追加し、チャットで👺ラベルで再依頼）

</details>

## 裁定待ち

### 👺XX-Q1: <質問要旨>

（選択肢は「XX-Q1a」のように回答可能な形で簡潔に書く）
- a (推奨): …
- b: …

（推奨理由を簡潔に書く）

#### 背景説明 (基本省略、詳細を求められたら補充)

## 確認待ち

### 👺XX-C1: <確認要旨>

#### 確認手順 (基本省略、複雑な場合のみ)

（確認してほしい内容を書く）
- 箇条書きで簡潔かつ具体的に

```

## 統括固有の観点

- **Q は意味論から書く**: 「(a) 暫定 vs (b) 他候補 vs (c) 保留」でなく、原意図 /
  選択肢の意味論的な違い / 統括推しの根拠を明示 (worker 観察のラベル貼りで並べるのは
  `role-main-context` §2.2 の失敗パターン)
- **C は「何を見れば済むか」を絞ってから出す**: 実装完了を丸ごと投げるのでなく、
  確認すべき対象と観点を絞る (= 自分で観測できることは全部やってから残りを出す、
  [[empirical-verification]] の「検証しきった後の振る舞い」)
- **裁定でないものを裁定として投げない**: 着手順・作業の可否など自分で決められる
  ことは起票せず進める (`role-main-context` §1.4 自律進行)
- 複数論点が絡む Q は α/β/γ 分割 (独立軸に分ける)
