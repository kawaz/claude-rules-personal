# 業務文脈の固有名詞を public な成果物に書かない

**判定軸は「その成果物が public に出るか」の一点**。public に出るものには業務固有の
固有名詞・話題カテゴリを含めない。具体的な対象語は `identifiers-*.md`
(各 overlay リポ) で定義する。

## 要サニタイズ (= public に出るもの)

public リポ (kawaz/* の public) に入る一切:

- コミットメッセージ・PR タイトル/本文
- docs/, README, journal, handoff 等のリポ内ファイル
- コードコメント・識別子 (変数名・関数名)

## サニタイズ対象外

- **private リポの内容**。業務リポ・overlay リポ (`claude-rules-*` の private) ・
  private な個人リポは、中に業務固有名詞があっても問題ない
- ローカルに配られるだけのもの (`~/.claude*/` 配下の rules / skills / 設定)
- セッション内の会話・思考
- ユーザが明示的に「固有名詞含めてよい」と指示した場合

private を public 化するときは、その時点で中身をチェックする (= public 化が
サニタイズの発動点であって、private のうちは気にしない)。

## 一般化の例

| 業務固有 | 一般化 |
|---|---|
| 具体的な組織名 | 「ある業務先」「業務関連組織」 |
| 業務用 GitHub アカウント名 | 「業務用 GitHub アカウント」 |
| 業務リポ名 | 「業務リポ」「仕事用リポ」 |
| 業務固有プロダクト名 | 「業務プロダクト」 |
| 話題カテゴリ (特定業界・特定領域) | カテゴリ名を伏せて「ある業界」「特定領域」等 |

## 適用フロー

対象は public リポでの作業のみ。private リポではこのフローを回さない。

1. **Write/Edit 前**: 書き込み内容に対象単語・カテゴリが含まれていれば、書き込み前に一般化を提案
2. **コミット直前**: staged diff を確認、対象が含まれていれば commit を止めて一般化提案
3. **private → public 化するとき**: 既存の中身を通しでチェックする
4. **判断に迷ったら**: 該当箇所の書き込みを保留し、判断を仰ぐ (メインはチャット本文で kawaz に尋ねる、ワーカーは報告に含めて委譲元へ返す)

## 単語マッチと文脈判定

- **単語リスト** (`identifiers-*.md` の単語リスト) は文字列マッチでよい
- **話題カテゴリ** は単語列挙では弾けない。文脈判定が必要 (例: 「特定業界の業務文脈で書かれているか」)
- 単語が一般名詞と衝突する場合 (例: "party") は文脈判定に切り替え、業務文脈で使われているときのみサニタイズ対象

> **Why**: public リポへの業務情報流出防止。守るべきは「外に出ること」であって、
> 業務固有名詞が手元のどこかに存在すること自体ではない。private リポまで対象にすると、
> 業務面のルール・手順が自分の語彙で書けなくなり実用性を失う。
> 固有名詞の具体リストは各 overlay リポ (private) で管理し、本ルール (公開可能) には
> 仕組みだけを書くことで、common 層を public にしても情報漏洩しない構造を維持する。
