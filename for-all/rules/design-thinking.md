# 設計思考

## ワークアラウンドフィールド禁止

問題解決のために構造体にフィールドを追加するのは最終手段。

1. **既存の枠組みの組み合わせで解決できないか**を最優先で考える
2. 既存で無理でも、**そのフィールドが本当に正しい場所か**を疑う
3. 表示用メタデータのために実装を歪めるのは本末転倒

### チェックリスト

新しいフィールドや型を追加する前に:

- [ ] 既存の型・関数の組み合わせで表現できないか？
- [ ] クロージャで状態をキャプチャすれば不要にならないか？
- [ ] そのフィールドは本当にその構造体の責務か？
- [ ] ヘルプ表示等の「従」の都合で「主」のコア設計を歪めていないか？
- [ ] 将来の仮定的要件のために今の複雑さを増やしていないか？

## 目的と責務から書く

目的は**手段を変えても文が変わらない**形で書く (「設定ファイルを JSON で読む」でなく「設定を外部から差し替えられるようにする」)。書かれた手順の量から目的を逆算しない — 基盤が既に満たしている保証は手順に現れないので、逆算すると目的から落ちて、基盤を差し替えた瞬間に消える。**手順に現れない保証こそ目的に明記する**。

**何を増やしたくないかを目的と同格に置く**。制約より強く効き、後の判断がそこから導ける。増やしたくない対象が何を指すかも定義する (定義がないと「これは該当しない」で迂回される)。

着手前・仕上げのチェック項目は reference の `design-spec/` を読む。

## 作業箇所の責務を先に確かめる (設計でもコーディングでも)

今触っているライブラリ・crate・関数が **何をすることが責務で、何を保証し、何を保証しないか** を常に前提に置く。論点に気づいたら「対処すべきか」でなく **「これは作業箇所の責務か」から問う**。対処できるものは全部対処すべきに見えるので、前者で入ると余計な対処と設計が積み上がって芯が見えなくなる。

- **責務内**: 対応する。今やらないなら issue にする
- **責務外**: 対処も設計 (DR・仕様・裁定の問い) もしない。「xxx はこの関数 / crate の責務外」と **日本語 40 文字以内の一文** を境界の記述として残して終える。消費する側 (呼び出すアプリ・CLI) の話は、その側の中で決める
- 未実装の関数や設計文書の節が既にあることは、それが責務である証拠にならない

気にすること自体は止めない。気にした内容を責務の確認にかけてから扱いを決める。
