# TypeScript の型の付け方の水準

TypeScript を書く時は、型の付いていない値が境界より内側に流れ込む経路をゼロにする。スキーマ (valibot / zod 等のバリデータ) を使う場所は、外から値が入る境界と、プロトコルの設計が絡むところ。それ以外は必要性を判断する。

## スキーマを使う場所

- **外から来るデータは受け取った境界でスキーマに通す** (JSON、外部コマンドの出力、ファイル、HTTP / WebSocket、ストレージ、stdin、CLI の引数)。結果は型付きの値か型付きの失敗にする。「validate して使う」ではなく「parse して型を付ける」(`JSON.parse` は文字列を値にするだけで parse ではない)
- **プロトコルの設計が絡むところ** (プロセスやパッケージをまたぐ形、送る側と受ける側が共有するメッセージ) は、形をスキーマで定義し、型はそこから導く。型とスキーマを別々に書かない
- スキーマのライブラリはプロジェクトで 1 つに決める (スキーマから型を導け、失敗を値で返せるモダンなもの)

## それ以外は必要性を判断する

ライブラリの公開 API や内部の関数のように、呼び出し元が TypeScript で型を満たす場所には、スキーマを入れない。型を信じて書き、実行時に残すのは壊れた出力を避けるための素朴な検査 (範囲、個数) だけにする。バリデータを足す前に「この値は実行時に外から来るか」「形を共有するプロトコルか」を自問する。足すと依存と bundle が増え、公開する型にも内部の型が漏れやすい。

## 型の水準 (どこでも)

- **関数の引数と戻り値は具体的な型で書く**。`unknown` を受けて中で調べる関数を作らない。`unknown` が出てよいのは `catch` の束縛と、スキーマに通す直前の境界の 1 か所だけ
- **`as` による型の主張 (`as const` を除く)、`any`、非 null の主張 `!` は使わない**。型が合わない時は主張で黙らせず、境界ならスキーマに通し、それ以外は型の設計を直す (値が無い場合は型で表して分岐で扱う)。リテラルや定数への主張は `satisfies` か型注釈に置き換える
- **lint で機械的に検査する**。typescript-eslint / oxlint の該当規則を有効にする

## 自警

- 外から来る値を `as Foo` / `x!` で通している、`(x: unknown)` を受ける関数を作っている、`isRecord` / `typeof x === "object"` を重ねている (境界でスキーマに通していないサイン)
- 型どおりに呼ばれるはずの内部関数や公開 API に、バリデータを入れようとしている (必要性を判断していないサイン)

境界の書き方の具体例と lint の設定は reference の `typescript/schema-first-typing` を読む。

Why: 外から来る値は型を満たす保証が無く、検査の漏れが実害になる。一方、型を満たす呼び出し元にまでバリデータを足すと、依存と複雑さだけが増える。
