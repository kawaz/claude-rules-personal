# 裁定・確認待ちは docs/QUESTIONS.md に常時集約

リポ管理プロジェクトの `docs/QUESTIONS.md` に、ユーザの判断が要る **裁定待ち
(Q)** と、実装完了して実機確認を待つ **確認待ち (C)** を集約する。リポの無い
作業では適用外。

**AskUserQuestion は使用禁止** (タイムアウト無しで無限待ち、リモート応答不可、
ユーザ入力中の割り込みが不快)。代わりに本ファイル + 👺 参照で依頼する。

## テンプレート (運用規約の本体)

ファイルが空ならこれをコピーして書き始める。**運用規約は冒頭の引用ブロックが
正本** — 以降の節はそこに書けない補足だけを持つ。

```markdown
# 裁定・確認待ち一覧 (ユーザ用)

> 運用規約 (ゼロコンテキスト読者向け、正本は claude-rules-personal の
> `questions-md-registry` rule):
> - 裁定待ち = ユーザの判断が要る項目。確認待ち = 実装済みで実機確認を待つ項目
> - ラベルはバッチ / セッション毎に一意な短プレフィクス (XX-Q1 / XX-C1 形式、
>   Qn 単独の使い回し禁止、長期一意性は不要)
> - 👺 は「いま待っている項目」とチャットの依頼文にだけ付ける
>   (裁定済み・過去参照に付けない。誤陽性がユーザのアラームを汚す)
> - チャット提示と同一ターンで本ファイルに記録 + path 指定 commit
>   (push はリリース窓に同乗)
> - 載せるのはユーザが今答えられる / 今確認できる形になったものだけ
>   (調査中のものは載せない)
> - 裁定が下りたら該当セクションを即削除し、内容は正規の記録先 (DR / issue /
>   journal / close_reason) へ反映。本ファイルは常に「現在待ち」だけを持つ
> - 確認待ちの削除条件: ユーザが確認 OK を返した / 後続リリースで当該実装が
>   上書きされ確認対象でなくなった
> - 1 項目 = 1 セクション、選択肢は箇条書き。粒度は索引 (詳細の正本は
>   findings / issue / DR 側に置き複製しない)
> - 参照パスはリポ内相対 (リポ外はフルパス)

## 裁定待ち

### 👺XX-Q1: <質問要旨>
- a (推奨): …
- b: …

#### 背景説明 (初回は省略、詳細を求められたら補充)

## 確認待ち

### 👺XX-C1: <確認要旨> (vX.Y.Z)
確認してほしい内容を簡潔に。実装したバージョンを添える。

#### 確認手順 (基本省略、複雑な場合のみ)
- 箇条書きで簡潔かつ具体的に
```

## テンプレに書けない補足

- チャットは「👺TNG-Q1 の裁定お願いします」の 👺 + ラベル ID 参照だけにする。回答は「SEC-Q6=a」のようにラベル + 選択肢記号で通じる形
- 👺 のハイライト / アラームはユーザ側で `👺\s*[A-Za-z0-9α-ωΑ-Ω\-]{2,}` の正規表現を使っている
- 選択肢を 1 行に詰め込まない理由: 横に長いと読みにくい (kawaz 2026-07-23)
- 回答が新しい Q を生んだ場合 (前提棄却・逆質問)、旧 Q の削除と新 Q の追記を同時に行う

### 説明を求められたらファイル内で補充する

「説明して」「詳しく」「それ何?」と返されたら、**チャットで長々説明しない**
(TL に流れて参照コストが高い)。当該 Q を「#### 背景説明」等のサブセクション
付きで**書き直して再提示**し (self-contained に)、チャットは「👺HO-Q5 を説明
付きで再提示しました」の参照だけ返す。前提知識が要る Q は初回から説明を添える
のが望ましい (kawaz 確認「説明が TL に流れず良い感じ」)。

## Why

- ユーザが「何待ちか」をチャット履歴から掘り返す手間削減
- AI にリストと説明を再生成させるコストの削減 (今何待ち? を撲滅)
- セッション境界・並行セッションを越えて裁定・確認キューが共有される
- 確認依頼は特に流れやすい: 「実機確認お願いします」の直後にユーザが次の要望を投げると TL に流れ、何が未確認か双方分からなくなる (kawaz 2026-07-26)
