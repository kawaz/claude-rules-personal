# いつものワークフロー

標準やベストプラクティス、t_wadaのTDD、過度に複雑にしないことを常に意識して進行する。

キリの良いタイミング（計画完了、実装完了、各ラウンドの修正完了など）で適切な粒度でコミットしながら進める。

## `/simplify` と `/itumono-full-review` の責務分離

両者を混同しないこと。

- **`/simplify`**: コード整理 (重複排除 / 抽象化 / 過剰実装の削減 / 命名統一)。
  挙動を変えず実装を綺麗にする refactor。
- **`/itumono-full-review`**: 設計・ロジック・セキュリティ等の **意味的な問題** 検出。
  バグや脆弱性、仕様逸脱を見つける。

`/simplify` を review skill 代用にしない。逆に review で「重複排除すべき」を指摘しない。
fix loop は review → 修正 で進め、整理が必要なら別フェーズとして `/simplify` を挟む。

## 完全自律モード時の AskUserQuestion 抑制

引数または呼び出し元（`/itumono-nonstop` 経由など）で自律度が **「完全自律」** と指定されている場合、ユーザ不在が前提のため本ワークフロー中で **AskUserQuestion を一切呼ばない**。AskUserQuestion はタイムアウトせず、不在時に呼ぶとセッションが停止する。以下を自己判断でスキップして進む:

- **開始フェーズの選択** — 引数指定がなければ「実装から（フェーズ3）」を既定とする
- **フェーズ1（要件定義インタビュー）** — 会話コンテキスト・既存のDR/設計書から要件を確定する
- **フェーズ1.5（自律度確認）** — スキップ（既に完全自律で確定済み）
- **フェーズ2.5（計画の方針確認）** — スキップ。計画はDRに記録し、レビューループ（フェーズ4）の検証に委ねる

設計の根幹に関わる判断が必要になった場合は、AskUserQuestion を呼ばず、その判断を保留にして他の作業に進む（`/itumono-nonstop` の停止条件に従う）。

## 開始フェーズの選択

引数で指定がなければ AskUserQuestion で確認:

- **要件定義から**: ゼロから始める（フェーズ1へ）
- **実装から（推奨）**: 設計書・DRが既にある（フェーズ3へ）
- **レビューから**: 実装済み、レビュー+修正のみ（フェーズ4へ）

## フェーズ1: 要件定義

AskUserQuestionでインタビューし、要件を明確にする。不明点がなくなるまで繰り返す。

（完全自律モード時はインタビューせず、会話コンテキスト・既存DR/設計書から要件を確定する。冒頭の「完全自律モード時の AskUserQuestion 抑制」を参照）

## フェーズ1.5: 自律度確認

要件が固まった後、AskUserQuestionで実装中の自律度を確認する（完全自律モード時はスキップ）:

- **自律的に進めてOK（推奨）**: 判断に迷う場合のみ確認
- **要所で確認**: 主要な判断毎に確認
- **完全自律**: 確認なしで完了まで進行。離席・就寝時向け。

## フェーズ2: 計画作成

計画をDesign Record（DR）としてドキュメント化し、コミットする。レビューループ（フェーズ4相当）でレビュー・修正する。

## フェーズ2.5: 計画の方針確認

初回の計画をユーザーに提示し、方針に問題がないか確認する。OKが出たら以降は選択した自律度に従って進行する。

（完全自律モード時はスキップ。計画はDRに記録し、レビューループの検証に委ねる）

## フェーズ3: タスク分解と実装

`/decomposition.ja` を実行してタスクを分解し、TDD で実装する。

## フェーズ4: レビューループ

以下の停止条件すべてを満たすか最大反復回数に達するまで繰り返す。

**停止条件 (全部 AND):**
1. 最新ラウンドで **Critical / Warning なし**
2. 最新ラウンドの **Info も対応可能なものは対応済** (= 残置 backlog file の info 対応率 80% 以上)
3. **最低 2 ラウンド完了**

**手順:**
1. 初回のみ: `/simplify` でコード整理してからコミット
2. `/itumono-full-review` を実行 (= 残置 backlog file `/tmp/itumono-backlog-{repo}.md` を読込 / 追記)
3. Critical/Warning あり、または info 対応率が低い → 修正してコミット
4. 修正に **breaking change** (= 既存 user / script の挙動を変える変更) を含む場合は、
   ラウンド完了時にユーザに **明示申告** する (= 静かに main に入れない)
5. backlog が空 + 上記停止条件を満たすまで 2 に戻る

### breaking change の申告例

- API シグネチャの変更 (戻り型 / 引数追加)
- CLI 入力フォーマットの破壊的変更 (`--timeout=5` → `--timeout=5s` 必須化など)
- 設定ファイルの schema 変更
- exit code 体系の変更
- env variable 名 / format の変更

これらは「commit message に書く」だけでは不十分。push 前にユーザへの一次申告
(= 「これ breaking ですよ、進めて良いですか」) を入れる。完全自律モード時は
申告は journal / DR に記録、ユーザ復帰時に「breaking change のサマリ」として提示。
