# Non-Stop 戦略

ユーザが離席・就寝中でも、1つのタスクが完了するたびに次の作業を自律的に見つけて継続する。

## ユーザ不在時の禁止操作

**以下は絶対に実行しない:**

1. **AskUserQuestion** — タイムアウトがないため、ユーザ不在時に呼ぶと無限に待機してセッションが死ぬ。代わりに自分で判断する
2. 上記に該当する操作が必要になったら、**スキップして他の作業に進む**

git/jj/ssh 関連の署名操作（push, fetch 等）は通常通り実行してよい。1Password エラーが発生した場合は `1password-error-notification.md` ルールに従う。

## 動作原理

```
while true:
  1. タスクを `/itumono-full-loop` で実行（自律度: 完全自律）
  2. 完了したら次にやるべき作業を自律的に考え抜く（後述）
  3. 見つかれば 1 に戻る
  4. どうしても見つからなければ停止してユーザに報告
```

## 作業前の依存グラフ化

実作業開始前に、見えているサブタスクは **`TaskCreate` で粒度ごとに登録し、
`addBlockedBy` で依存順を明示**する。途中で新たに浮上したタスクも随時 `TaskCreate`。

理由:
- 途中で文脈が切れても（セッション再開、サブエージェント委譲）残タスクが残る
- 「どの順で進めるか」を一度決めたら機械的に進められ、思考コストが減る
- 完了したタスクから unblock が連鎖するので「次に何をやるか」の判断が即決
- ユーザへの進捗可視化にもなる

作業途中で依存関係が変われば `TaskUpdate` で更新。使い捨て感覚でよい。

## 次タスクの探し方

**止まらないことが最優先。** タスク完了のたびに、直接的な残作業と多角的な視点の両方から次の作業を探す。

### 直接的な残作業
1. **TODOリストの未完了タスク** — TaskList で残タスクを確認
2. **`/tmp/itumono-backlog-{repo}.md` の残置** — `/itumono-full-review` が書き出した
   過去ラウンドの Critical/Warning/Info 残置。`[done]` マークが付いてない項目は次タスク候補
3. **レビュー指摘の未対応項目** — 直前のレビューで Info 扱いにした改善点 (= 2 と被るがコンテキスト内の指摘も)
4. **関連する改善** — 実装中に気づいた改善点、テスト追加、ドキュメント整備
5. **コード品質** — lint、型安全性、エラーハンドリングの改善
6. **中程度の設計判断** - アーキテクチャの根幹が覆る程ではない設計判断はDR作成とともに自律的に行う

### 異業種ペルソナによる発見（毎回実施）

直接的な残作業の有無にかかわらず、**毎回ランダムに2〜3職種を選んで**プロジェクトを見直す。ユーザ自身が気づいていない改善点を掘り起こす。同じ職種の繰り返しを避け、多様な視点を確保する。

ペルソナ例（毎回ここから選ぶ、これ以外も自由に発明する）:
- **法務**: ライセンス整合性、依存ライブラリのライセンス確認、NOTICE ファイル
- **テクニカルライター**: README、CONTRIBUTING、API ドキュメント、コメントの品質
- **セキュリティエンジニア**: 入力バリデーション、依存の脆弱性、シークレット漏洩
- **QAエンジニア**: エッジケース、境界値テスト、異常系テスト、フレーキーテスト
- **UXデザイナー**: CLI のヘルプ文、エラーメッセージの分かりやすさ、デフォルト値の妥当性
- **DevOps**: CI/CD改善、ビルド時間短縮、キャッシュ最適化
- **経理**: コスト（CI時間、バイナリサイズ、依存数）の最適化
- **マーケティング**: CHANGELOG、リリースノート、デモ・サンプルの充実
- **ゲーマー**: パフォーマンス、ベンチマーク、最適化の余地
- **子供（初心者）**: 初めて触る人がつまずくポイント、Getting Started の分かりやすさ
- **アクセシビリティ専門家**: 多言語対応、エラーコード体系、マシンリーダブルな出力
- **競合分析者**: 類似ツールとの比較、差別化ポイント、不足機能
- **建築家**: 構造の美しさ、モジュール境界、責務の明確さ
- **探偵**: 隠れたバグ、未処理のエラーパス、暗黙の前提条件
- **野生のデバッガー**: ゲームのバグハンターのように「なぜか壁に挟まると裏世界に行ける」的な異常系を本能で嗅ぎ出す。想定外の入力順序、タイミング、境界条件の組み合わせ
- **犯罪者/ハッカー**: 技術や仕様の抜け穴を悪用する視点。権限昇格、入力偽装、レースコンディション、サプライチェーン攻撃。防御側の改善に直結する

直接的な残作業とペルソナ発見の両方から候補を集め、価値の高い順に `/itumono-full-loop` で取り組む。
必要なら新規TODOリストの追加も行う。

### 停止（最終手段）

上記すべてを尽くしてなお作業が見つからない場合のみ停止。

## 外部依存の調査は並列で

「このツール/API でこの情報が取れるか」「この挙動は本物か」を調べるとき、
**仮説が複数ある場合は Agent を並列起動**して手分けさせる。

- 1つの仮説を深掘りする時間で 3-4 の仮説を並列検証できる
- 各 Agent の結果が返るのを待つ間にメインコンテキストで別作業も進行可能
- 結果が出揃ってから統合判断すれば、早まった採用で後戻りする無駄を防げる

例: 「rate_limit 情報の取得経路」を調べるとき、`/v1/messages` 直叩き・バイナリ
解析・fs_usage 観測・MCP チャネル探索を同時に並列起動し、最も筋の良いものを採用。

## 「使えないと決めつける前に」

仮説が詰まっても、**既存コードベースに過去の成功例がないか**を必ず確認する。

- 「昔作ったCLI」「古いコミットで消された機能」「使われていないユーティリティ」
- `git log -S 'キーワード'` や `git log --all --oneline` で削除済みコードまで遡る
- 過去のユーザ自身の実装が最短ルートになることが多い

ユーザから「昔 XXX 作った」等のヒントがあれば最優先で辿る。

## 制約

- **破壊的操作は行わない** — force push、ブランチ削除、本番環境への操作は停止してユーザに確認
- **設計判断が必要な場合は停止** — アーキテクチャ変更、API 設計変更など
- **各タスク完了時にコミット** — 作業の区切りで必ずコミットし、成果を失わないようにする
- **push も適宜実行する** — コミット後に push してリモートに反映する

他者リポジトリへのコントリビューション文脈での制約（PR 作成前の確認等）は
`itumono-contribute` 側に書かれている。本スキルは個人プロジェクトでの自律作業が
主用途なので、PR/Issue を当たり前には作らない前提で動く。

## 停止条件

以下のいずれかで停止し、ユーザにサマリを報告する:

- 全ての探索を尽くしても作業が見つからない
- 設計の根幹に関わる設計判断やユーザ確認が必要な作業以外にやれることがない

## 報告

停止時に以下をまとめて報告する:

- 完了したタスク一覧
- 各タスクの成果（コミット、変更ファイル）
- push 済みコミット一覧
- 試したペルソナとその視点からの所見
- メタ報告（有用なペルソナの発明、スキルの改善提案）
- 停止理由
- 次にユーザが判断すべき事項
