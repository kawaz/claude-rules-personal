# 裁定・確認待ちは docs/QUESTIONS.md に常時集約

プロジェクト内の `docs/QUESTIONS.md` に、ユーザの判断が要る項目を集約する。

**AskUserQuestion は使用禁止** (タイムアウト無しで無限待ち、リモート応答不可、
ユーザ入力中の割り込みが不快)。判断が要る時はチャット本文で尋ね (自由文回答歓迎)、
裁定を待つ間に他の作業へ進められるなら本ファイルに 👺ラベル付きで起票して参照する。

常時ロード rule でなく skill なのは、ユーザと直接コミュニケーションを取るのが
メインコンテキストだけだから (= ワーカーは AskUserQuestion も QUESTIONS.md への
起票も行わない)。メインは `load-role-main` から invoke するので常にロード済み。

`for-all` に置くのは、各業務 overlay がこの一般規約を土台に差分ルールを重ねる
構成のため (例: emeradaco はファイル名・commit 有無・スコープを差し替える)。
`for-me` だと self repo のセッションにしか配布されず、overlay 側の差分ルールが
土台を失う。

## Why

- ユーザが「何待ちか」をチャット履歴から掘り返す手間の削減
- AI にリストと説明を再生成させるコストの削減 (今何待ち? を撲滅)
- 実装完了や質問提起が散発的に発生してTLに流れてしまい、未確認のまま亡失される問題を、本ファイルが解決する
- セッション境界・並行セッションを越えて裁定・確認キューが共有される

## テンプレート

`docs/QUESTIONS.md` が無い / 空のときは
`${CLAUDE_SKILL_DIR}/QUESTIONS.template.md` をそのままコピーして使う
(運用規約は当該ファイルの `<details>` 節が正本)。

## 書き方 (実際に誤読された 2 点)

- **背景説明を書かない**。折りたたみ節に逃がすのも不可 — 隠してもコンテキストは
  食う。1 項目は「要旨 1 行 + 選択肢 + 理由 1-2 行」で完結させ、絶対に説明が要ると
  判断したときだけ書く (求められたら足す)
- **ラベルの prefix は 2-3 文字**。意味が通らなくてよい (`RS-Q1` で十分、
  `RESUME-Q1` は長い)。読む側の負担を増やさないことが目的

## 統括固有の観点

- **Q は意味論から書く**: 「(a) 暫定 vs (b) 他候補 vs (c) 保留」でなく、原意図 /
  選択肢の意味論的な違い / 統括推しの根拠を明示 (worker 観察のラベル貼りで並べるのは
  `role-main-context` §2.2 の失敗パターン)
- **C は「何を見れば済むか」を絞ってから出す**: 実装完了を丸ごと投げるのでなく、
  確認すべき対象と観点を絞る (= 自分で観測できることは全部やってから残りを出す、
  [[empirical-verification]] の「検証しきった後の振る舞い」)
- **裁定でないものを裁定として投げない**: 着手順・作業の可否など自分で決められる
  ことは起票せず進める (`role-main-context` §1.4 自律進行)
- 複数論点が絡む Q は α/β/γ 分割 (独立軸に分ける)
