# 設計規範 (kawaz 起草、2026-09-07)

何かを設計・規定するときに、着手前・作業中・仕上げに確認すること。適用例: ccmsg の
`docs/design/mesh-peer-auth.md` / `mesh-self-identification.md`。

常時ロードの rule と重なる項は本文を短くし、rule 側を正本とする: §3.4 (廃止したものへの
言及を消す) = `no-historical-noise`、§4.1 (宣言と実行を混同しない) = `role-main-context` §2.4、
§1.4 / §2.5 (増やさない対象・やらないことの明示) = `self-written-rule-blind-spots` の対極確認、
§2.5 の不採用表 = `document-design-rationale`。

---

## 1. 着手前に固めること

### 1.1 目的を、解の形に汚染されずに書く

判定基準は「手段を変えてもこの文が変わらないか」。

```
悪い: 設定ファイルを JSON で読み込む
良い: 設定を外部から差し替えられるようにする
```

YAML に変えれば前者は書き直しになるが、後者は変わらない。前者は手段であって目的ではない。

主語と動詞があるかは形式の話にすぎない。悪い例にも主語と動詞はある。

### 1.2 手順の量から目的を逆算しない

目的を満たすために基盤を選ぶと、その基盤が既に満たしている部分は手順に現れなくなる。書かれた手順から目的を逆算すると、現れていない部分が目的から欠落することがある。

受付を例にとる。目的は「窓口と来訪者が互いに相手を確認する」ことである。来訪者の側は、建物と看板を見れば相手が確認できるので、手順として書くことがない。一方、窓口が来訪者を確認する手順は、身分証の提示、名簿との照合、と手数がかかる。

結果、手順書は窓口側の記述ばかりになる。これを読んだ人は、目的が「窓口が来訪者を確認すること」だと受け取る。実際は相互確認が目的で、片方は建物という基盤に任せていただけである。

この誤解は、基盤を差し替えたときに表面化する。出張窓口を始めた途端、来訪者が相手を確認する手段が消えている。手順に書かれていなかったので、誰もそれが保証されていたことに気づいていない。

手順に現れない保証こそ、目的として明記しておく必要がある。

### 1.3 スコープの粒度を決める

目的は粒度に紐づく。粒度が定まらないと目的が書けない。

「システムを安全にする」は粒度が大きすぎて、権限分離も暗号化も全部入ってくる。絞ることで初めて外側を切り出せる。

### 1.4 何を管理したくないかを明示する

制約より強く効く。「増やさない」対象を目的として同格に置くと、後の判断がすべてそこから導ける。

増やしたくない対象が何を指すのかも定義しておくこと。定義がないと、後の人が「これは該当しない」と解釈して迂回できてしまう。

### 1.5 前提条件を列挙し、満たさない場合を併記する

「満たさない場合どうなるか」を書くと、それが本当に前提なのか、単に自分が要求しているだけなのかが判別できる。後者なら、他者の責務を自分の要求として書いている疑いがある (§2.2)。

## 2. 決めるときに守ること

### 2.1 論点に気づいたら「誰の責務か」から問う

「対処すべきか」から入ると、対処できるものは全部対処すべきに見える。エージェントも人間も、気づいた論点を潰さないのは手抜きに見えるため、書き足すほうに倒れる。

一つ一つは正しいので止まらない。正しいものが積み上がるほど、どれが芯なのか読み手に判別できなくなる。一見きっちりやっているように見えて、そもそも考える必要がなかったものが大半、という状態になる。

「誰の責務か」なら、自分の責務でないものが最初の分岐で落ちる。判断の根拠は目的である (§1.1)。目的が曖昧なままだと責務も判定できず、結局「対処できるからする」に戻る。

### 2.2 責務外のものは、境界の記述として残す

無視でも対処でもない第三の置き場を作る。「これは扱わない、なぜなら他者の責務だから」と書いておけば、後の人が同じ論点に気づいたとき、判断済みだと分かる。

前提条件が増えていくときは、境界の引き方を疑うこと。責務の範囲が曖昧なままだと、他者の責務を自分の要求として書いてしまう。

### 2.3 実装に裁量を残してよい箇所とそうでない箇所を区別する

複数の実装が同一の結論に達する必要がある箇所は、仕様側で規則を固定する。何でもよいが一つに決める、が正しい。裁量に残すと、双方が異なる結論を出して壊れる。

結論が一致する必要がない箇所は、意図だけを規定して形式は任せる。URL の形やメッセージフォーマットなど。要件は性質として書く。

この区別を誤ると、規定すべきを曖昧にし、任せるべきを縛る。

### 2.4 曖昧な数値を書かない

「適切な値」「過大でない」と書くのは、決めるべきことを実装に投げている。推奨値と根拠を書く。根拠があれば、状況が違う実装者が自分で調整できる。

### 2.5 やらないことを、理由と目的への紐づけとともに書く

理由なしの禁止は制約に見え、後の人が回避したくなる。「目的の後段に反する」のように参照先を書いてあれば、追加を検討した人は「では目的のほうを見直すべきか」という正しい問いに着地する。目的が変わったなら追加は正当なので、判断が上のレイヤに上がるだけで、間違った追加にはならない。

不採用にした選択肢は表として残す。実装者が思いつきうる近道は、明示的に潰しておく。

### 2.6 機能を足して管理が減るなら、進む方向は合っている

通常は逆になる。噛み合っている設計では、要素を足したことで別の要素が不要になることがある。そういう噛み合いが出るなら、目的と手段が一致している。

### 2.7 やらないことに反する変更を検出するテストを書く

文章は読まれないことがあるが、CI は必ず読まれる。設計の核が「持たない」「増やさない」という形をしているとき、それを壊す変更は改善に見えるため、文章の禁止では止まらない。核が保たれていることをテストにしておく。

## 3. 仕上げに確認すること

### 3.1 全体を通読する

指摘のたびに該当箇所だけ直すと、残骸が残る。前提が変わった後も古い記述が生き残り、文書内で矛盾する。個別対応を数回続けたら、一度通しで読む。

### 3.2 目的が確定する前に書いた部分を疑う

目的が後から明確になった場合、それ以前の記述はすべて別の前提で書かれている。特に、代替案の評価や前提条件は書き直しが要る。

### 3.3 相互参照を機械的に検証する

節番号の参照は、節を追加・移動するたびに壊れる。手で追わない。

```python
heads = set(re.findall(r'^#{2,3} (\d+(?:\.\d+)?)\.? ', s, re.M))
refs  = set(re.findall(r'§(\d+(?:\.\d+)?)', s))
print(sorted(refs - heads))
```

### 3.4 廃止したものへの言及自体を消す

方針を変えたとき、「なぜ旧案を採らないか」を本文に書き足したくなる。自分の判断を正当化したくなるためだが、読み手には存在しない選択肢の否定を読まされるだけである。

消す。不採用の記録が要るなら、末尾の不採用表に一行だけ残す。本文中に残す理由はない。

これは頻出する。手直しを重ねるほど、廃止済みの前提に基づく記述が本文に堆積していく。通読時 (§3.1) に最も多く見つかるのがこれ。

### 3.5 章立ての順序と分量のバランスを確認する

思いついた順に書き足していくと、文書は追記順のまま積み上がる。前半に問題提起がないのに結論めいた記述が現れる、といった構成になり、そのまま放置されやすい。

読む順序で並んでいるかを見る。前提のない結論、参照先が後ろにある説明、この時点では判断できない選択肢の提示があれば、位置が違う。

分量の偏りも手がかりになる。ある節だけが突出して長いなら、そこに複数の主題が混ざっているか、他が書き足りない。逆に一行しかない節は、他に統合できることが多い。

### 3.6 削って良くなるかを試す

説明が 3 箇所に分散していたら 1 箇所にまとめる。不採用の話が本文中央にあったら末尾に移す。削ると目的が効くようになることが多い。

### 3.7 全文を規範と照らし合わせる

修正が一巡したら、最新の理解のうえで全文を本規範と突き合わせる。個別の指摘に対応している間は視野が局所化しており、規範に反する箇所が残る。

## 4. 作業上の注意

### 4.1 宣言と実行を混同しない

「直します」と書いて手を動かさずに終える、が起こりうる。作業を伴う結論を出したら、その場で実行する。

### 4.2 バージョン管理のない環境では版を残す

VCS 下ならこの節は不要。そうでない環境 (チャット、一時的な作業ディレクトリなど) では、修正で悪化したときに戻す手段がないため、書き換える前に旧版を別ファイルとして残す。
